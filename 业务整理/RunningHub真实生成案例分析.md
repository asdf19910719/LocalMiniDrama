## 3. 风格怎样作用于“周启”

### 3.1 继承关系

本剧集的 5 个资产都没有设置局部 `stylePresetId`，因此全部继承剧集的全局风格 `266`。这意味着“周启”不是仅在卡片上显示风格名称，而是实际进入了全局风格的提示词编译链路。

角色原始数据为：

- 姓名：周启
- 身份：男，青年，独自出差的职场人士
- 性格：谨慎多疑，反应敏捷
- 层级：主元素

### 3.2 客户端编译逻辑

当前公开前端构建显示，角色生成会把以下字段交给角色专用提示词编译器：

```text
styleLabel       = 现代都市悬疑风格
stylePrompt      = 上述完整风格提示词
assetType        = full_body_front_plain
name             = 周启
identity         = 男，青年，独自出差的职场人士
appearance       = 角色外貌字段（本案例原始数据未提供明确值）
costumes         = 角色服装字段
contentLanguage  = zh
```

编译器输出正向 `prompt` 和负向 `negativePrompt`。调用生成接口时，正向结果会作为 `promptOverride` 提交；所以风格提示词不是只保存为一个 ID，也不是只拼接“现代都市悬疑风格”几个字，而是与角色身份、外貌、服装、资产构图约束共同编译。

角色资产层还会加入“单人、正面、全身、纯净背景”等资产用途约束，并排除三视图、多视图、转面图、多角度、背面/侧面、分镜、角色设定卡、多人、复杂背景和场景等干扰项。由此可见：

```text
最终角色提示词
  = 角色事实
  + 全局风格名称
  + 全局完整风格提示词/结构化维度
  + 角色资产构图规则
  + 正向质量词
  + 负向质量与内容约束
```

### 3.3 模型选择

风格 `266` 自带默认文生图模型键 `NANO_PRO_T2I_OFFICIAL`。客户端的通用选择优先级是：

1. 当前素材或用户手动选择的模型；
2. 与风格 `t2iModelKey` 匹配的模型；
3. 页面默认模型。

当前项目资产偏好同时保存了 `characterAppId = 31`、角色参数 `16:9 / 1k`。因此“周启”的历史请求存在项目模型偏好覆盖风格默认模型的可能。生成历史接口只返回任务状态、结果图和费用，不返回最终请求体，当前证据不足以把“周启”的成功任务断言为某一个具体模型。

后续对“苏妍｜白色衬衫”的现场生成则给出了直接证据：生成面板实际显示模型为“全能图片G2-低价渠道版”，而不是风格 `266` 的默认 `NANO_PRO_T2I_OFFICIAL`。这证明实现参考时应保留“素材/用户选择 > 风格默认 > 系统默认”的显式优先级，不要把风格与模型一对一硬编码。

### 4.2 三视图规则与风格规则分工

当前公开客户端代码明确把用户界面的“角色三视图”映射为 `TURNAROUND`；另外，“三视图”快捷值也会映射为同一枚举。角色批量生成时，请求参数中会携带 `characterImageMode: "TURNAROUND"`。

公开客户端还包含一份“由参考单图转成三视图”的明确版式模板，其核心要求为：

> 生成横版 16:9 的正面、正侧面、背面三视图；严格保留五官、脸型、发型、肤色、年龄感、身材比例和服装；背景采用中性深灰渐变；左侧放半身/胸像特写，右侧放等距排列的完整三视图；脚底同一水平线、头顶同高；不要文字和乱码。

这份模板能够证明客户端如何定义 `TURNAROUND` 的构图语义，但它属于“参考单图转三视图”的公开客户端分支，不能直接等同为本次服务端收到的最终提示词原文。

本案例中可以把不同规则的职责拆开：

```text
苏妍角色事实
  + 白色衬衫服装事实
  + TURNAROUND 三视图版式/一致性规则
  + 全局风格 266 的冷灰、低照度、电影写实等视觉约束
  + G2 模型及 16:9 / 1k 生成参数
  → 1440×810 三视图结果
```

- `TURNAROUND` 决定“正面/侧面/背面、横版排布、角色一致性”等资产结构。
- `stylePresetId = 266` 决定“现代都市悬疑”的色彩、光影、材质、镜头气质及负面约束。
- “全能图片G2-低价渠道版”是本次真正选中的执行模型，覆盖了风格对象的默认模型键。
- 角色身份、外貌与服装字段决定画面中的人物内容，风格不能覆盖这些事实。

2. 产物本身的 `1440 × 810` 尺寸与三视图版式。

因此可以确定业务流程和规则分工，但仍不能把公开模板冒充为本次请求的逐字最终提示词。

## 5. 可以确定与不能确定的边界

### 可以确定

- 当前全局风格及完整真实风格提示词。
- 风格的结构化色彩、光影、材质、镜头、环境、质量和负面关键词。
- 资产未设置局部风格，因而继承全局风格。
- 前端会把完整风格提示词交给角色编译器，并将编译结果作为 `promptOverride` 提交。
- 风格提供默认模型键，但可被项目或素材模型偏好覆盖。
- “苏妍｜白色衬衫”本次实际使用“全能图片G2-低价渠道版”、`TURNAROUND` 三视图模式和全局风格继承。
- 本次产物为 `1440 × 810`，任务 ID 为 `2096628481294471170`。

### 当前不能精确确定

- “周启”这一次历史任务实际提交给服务端的完整最终正向/负向提示词原文。
- 服务端收到提示词后是否再次扩写、翻译、重排或追加隐藏提示词。
- 服务端是否使用额外参考图、LoRA、采样器或未公开工作流节点。
- 本次成功任务最终解析到的模型展示名和全部运行参数。

其中“最终模型展示名”这一限制仅适用于较早的“周启”历史任务；“苏妍｜白色衬衫”本次任务的展示模型已经现场确认，但采样器、步数、服务端工作流节点等参数仍不可见。

“周启”的限制来自分析开始时任务已经完成、早期请求记录已被清理；“苏妍”的限制来自网络记录虽提前启用，但调试事件在读取时异常。RunningHub 的生成历史/任务状态接口本身也不回传原始请求体。后续若要形成逐字提示词的一一对应证据，应在浏览器端增加稳定的请求体持久化代理或服务端可审计生成快照，而不能只依赖短期调试事件。

## 6. 对 LocalMiniDrama 的直接参考

建议实现为四层结构：

1. `StylePreset`：保存完整风格文本、结构化关键词、默认图片/视频模型键。
2. `ProjectStylePreference`：保存项目/剧集选中的风格、补充说明、画幅和模型偏好。
3. `AssetStyleOverride`：资产为空时继承全局，非空时局部覆盖。
4. `PromptCompiler`：按角色、场景、道具、分镜和视频分别编译正向/负向提示词，并记录可审计的最终请求快照。

尤其应新增“生成请求快照”：保存风格 ID、风格版本、编译前业务字段、最终正向/负向提示词、模型与参数。这样用户修改风格后，历史图片和视频仍能解释“当时为什么生成成这样”。

本次实证还说明三类配置必须分离保存：

- `stylePresetId`：控制视觉语言，允许全局继承和素材覆盖。
- `assetGenerationMode`：如 `SINGLE`、`TURNAROUND`、`DESIGN_SHEET`，控制资产版式和构图硬约束。
- `modelSelection`：保存用户实际选择及最终解析模型，允许覆盖风格推荐模型。

视频生成时也应沿用同一份风格快照，但不能复用图片三视图模板。视频提示词编译器应消费色彩、光影、材质和摄影语言，同时新增镜头运动、动作连续性、时序稳定性和首尾帧约束；`TURNAROUND` 只属于角色图片资产规则，不应泄漏进视频提示词。

### 7.4 “浏览器完整请求”与“模型最终提示词”不是同一个证据

本次已经能够逐字段确定浏览器请求体，但仍不能从浏览器侧取得服务端最终投喂模型的逐字提示词，原因不再是抓包失败，而是该文本根本没有从浏览器发送：

```text
浏览器请求体
  ├─ assetId / variantId：定位周启与灰色睡衣
  ├─ episodeId：定位剧集及风格 258
  ├─ appId：定位项目实际选择的 G2 模型
  ├─ characterImageMode = TURNAROUND：定位三视图规则
  └─ modelParams：16:9 / 1k
          ↓
RunningHub 服务端读取资产与风格数据并编译
          ↓
最终模型提示词（浏览器网络层不可见）
```

因此，后续若要证明“最终投喂模型的逐字完整提示词”，必须具备以下任一条件：

1. RunningHub 服务端日志或可审计的生成快照；
2. 生成接口响应中新增 `resolvedPrompt / resolvedNegativePrompt`；
3. 任务历史接口回传服务端编译后的提示词。

仅靠浏览器 Network 面板，即使成功抓到完整请求，也只能证明上述 JSON，不能证明服务端最终提示词原文。

### 7.5 与“单图引导生图”链路的区别

同一前端还存在“单图引导生图 / REFERENCE_FIRST”链路。该链路会在客户端显式编译角色正向提示词，并以 `promptOverride` 和 `styleId` 提交；标准直出三视图则不会提交它们。因此实现参考时不能把两条业务链路混为一谈：

| 链路 | 客户端是否提交提示词 | 风格传递方式 | 三视图处理 |
| --- | --- | --- | --- |
| 标准直出 `DIRECT` | 否 | 通过 `episodeId` 由服务端解析 `stylePresetId` | `characterImageMode = TURNAROUND` |
| 单图引导 `REFERENCE_FIRST` | 是，提交 `promptOverride` | 提交 `styleId`，客户端也参与风格编译 | 先单图，再按参考图派生后续视图 |

这说明 LocalMiniDrama 若参考 RunningHub，最好也显式区分“服务端上下文编译”和“客户端覆盖提示词”，并在生成快照中保存最终解析结果，避免仅凭请求字段无法审计实际模型输入。

### 8.5 全景场景的逐字提示词与规则

RunningHub 的“全景场景”需要区分两种入口。

#### 标准资产页直接生成全景

标准资产页选择“全景场景”时，仍调用：

```text

```

请求结构与 8.2 节相同，唯一关键变化是：

```json
{
  "sceneImageMode": "PANORAMA"
}
```

前端会把 `PANORAMA` 映射为 `21:9`，并在生成前检查所选场景模型是否支持该比例；但当前标准直出函数的 `modelParams` 仍只显式提交 `resolution`，不提交正向提示词、负向提示词或 `styleId`。场景名称、描述、风格 258 与全景规则最终由服务端解析。因此，标准资产页这次全景生成的“浏览器请求体提示词”仍然为空，不能伪造一段客户端未发送的完整模型输入。

#### 参考画布由“单图 + 俯视图”派生全景

参考画布中的“全景图”链路会显式构造 `promptOverride`，同时传入普通场景单图和俯视空间图作为 `referenceImageUrls`，请求画幅为 `21:9`。客户端中文固定模板的逐字原文是：

```text

```

模板末尾由客户端继续逐字追加：

```text
场景名称:{场景名称}。{场景源描述}
```

因此，某一具体场景在参考画布中的完整 `promptOverride` 为：

```text

```

这条链路的实际业务职责是：

```text
普通场景单图：提供画面内容、材质、光影和风格
  + 俯视空间图：提供空间结构、出入口和方位关系

```

需要原样保留的实现细节是：固定提示词内部写着 `宽高比 16:9 (--ar 16:9)`，但客户端真实 `modelParams` 为 `aspectRatio: "21:9"`。这是当前公开构建中的真实不一致；LocalMiniDrama 参考该流程时应统一为 `21:9`，不要复制这处冲突。

此外，这个派生全景模板不再次逐字拼入风格 258；它要求“风格必须与我给的单图保持一致”，即通过参考单图传递已生成的 90 年代写实电影视觉风格。标准资产页直接生成全景则仍通过 `episodeId` 交由服务端解析剧集风格。

```text
低质量，模糊，杂乱，畸变，多余物体，文字，水印，人物，角色，人，人脸，人手
```

#### 标准直出与参考画布的差异

| 链路 | 提示词传递 | 模型与画幅 | 风格生效方式 |
| --- | --- | --- | --- |
| 标准直出 `DIRECT` | 不提交 `prompt / promptOverride / negativePrompt / styleId` | 使用 `scenePropAppId = 40`；项目画幅，默认 `16:9 / 1k` | 服务端通过 `episodeId + assetId + variantId` 解析道具描述和风格 258 |
| 参考画布 `REFERENCE_FIRST` | 提交上述完整 `promptOverride` | 使用道具文生图模型；道具单图固定 `1:1` | 客户端把风格 258 编译进正向词，同时提交风格 ID 供服务端解析 |

道具没有 `characterImageMode` 或 `sceneImageMode`。它的核心硬约束是“仅一件道具、居中独立展示、中性干净背景、无场景、无其它物体、无人物”，不能把场景空间规则或角色三视图规则混入道具提示词。

### 8.7 俯视场景的逐字提示词与规则

RunningHub 的“俯视场景 / 俯视图”同样存在标准资产页直出和参考画布派生两条链路。

#### 标准资产页直接生成俯视场景

标准资产页选择“俯视场景”时，调用：

```text
POST /aivideo/assets/generate-image/async
```

相对于普通场景，关键请求字段变为：

```json
{
  "sceneImageMode": "TOP_DOWN"
}
```

其余仍使用当前项目和场景上下文：`episodeId = 2096647211023572994`、场景的 `assetId + variantId`、`scenePropAppId = 40` 及场景模型分辨率。标准直出请求不包含 `prompt`、`promptOverride`、`negativePrompt` 或 `styleId`；服务端根据剧集风格 258、场景描述和 `TOP_DOWN` 模式编译最终模型提示词。

客户端在提交前会对俯视模式执行专门的模型费用检查，并把场景模型及其配对文生图模型按最高分辨率计算。这说明标准俯视场景不是单纯把普通场景换一个画幅，而是由服务端编排的特殊场景资产流程；但浏览器请求仍不暴露服务端最终提示词原文。

#### 参考画布由场景单图派生俯视图

参考画布从普通场景“单图”派生“俯视图”时，会把该普通场景图作为唯一的 `referenceImageUrls`，显式提交 `promptOverride`，请求画幅固定为 `16:9`。该链路不再提交 `sceneImageMode: "TOP_DOWN"`，而是由提示词和画布节点类型表达俯视图语义。

当前客户端中文固定模板的逐字原文为：

#### 俯视图如何继承 90 年代写实电影风格

参考画布的俯视固定模板不再次逐字拼入风格 258，而是要求 `风格与单图的风格保持一致性`。完整链路为：

```text
风格 258 + 场景源描述
  → 先生成普通场景单图
  → 普通单图作为唯一参考图
  + TOP_DOWN 固定空间图模板
  + 场景名称与源描述
  → 16:9 俯视空间结构图
```

俯视图模板明确要求生成“图例、区域编号、文字说明、路线、指南针、入口、出口方向和比例尺”，所以不能套用普通场景的“禁止文字”负向约束。当前参考画布俯视请求没有单独提交 `negativePrompt`；文字和版式要求完全由上述 `promptOverride` 控制。

这套输出本质上是供分镜连续性使用的“空间关系设计图”，而不是普通电影镜头。LocalMiniDrama 参考时应把 `TOP_DOWN` 保存为独立资产类型，并保留它与普通场景图、全景图之间的派生关系。

## 9. “房客”项目的分镜剧本生成请求与处理流程（2026-09-07）

本节记录剧集 `2096647211023572994` 从“剧本”进入“分镜”步骤后，执行“AI 拆解分镜 / 生成分镜剧本”的前端真实调用。这里的“分镜剧本”是结构化镜头数据，不是后续生成的分镜图片。

### 9.1 浏览器实际提交的请求

若用户在生成弹窗中设置了分镜偏好、目标时长或时长模式，前端首先保存这些选项：

```text
POST /aivideo/episodes/storyboard-preference
```

请求体的逐字段结构为：

```json
{
  "episodeId": "2096647211023572994",
  "preference": "<用户填写的分镜偏好；未填写时为空字符串>",
  "durationMode": "standard",
  "targetDurationSec": null
}
```

其中：

- `preference` 用于填写叙事节奏、情绪重点或镜头风格；页面示例是“突出人物情绪，多使用近景和特写”。
- `durationMode = "standard"` 表示单镜头最长 15 秒；`adaptive` 表示单镜头最长 30 秒。
- `targetDurationSec = null` 表示自动估算；页面也支持 120 秒、180 秒或自定义正整数。

保存偏好成功后，前端启动真正的异步拆镜任务：

```text
POST /aivideo/episodes/generate-shots/async
```

本次生成请求体只有：

```json
{
  "episodeId": "2096647211023572994"
}
```

请求中没有 `prompt`、`systemPrompt`、`messages`、剧本文本、风格提示词、素材清单或 LLM 模型 ID。也就是说，浏览器没有把一段可截获的“逐字完整分镜提示词”发送给模型；它只保存业务参数，再用 `episodeId` 要求 RunningHub 服务端组装任务。

### 9.2 能看到与不能看到的提示词证据

当前证据可以逐字确认的“用户可控提示词”只有 `preference` 字段，其内容等于用户在分镜生成弹窗中填写的原文。若用户没有填写，该字段就是空字符串。

最终交给大模型的 system prompt、user prompt、JSON schema、剧本拼接格式、素材拼接格式和模型参数均未出现在公开前端请求或构建代码中。它们位于 RunningHub 服务端，因此不能仅凭浏览器把最终提示词逐字还原，也不能把分镜结果反推后冒充原始提示词。

服务端显然会依据 `episodeId` 读取生成所需的剧集状态，但公开前端证据只能证明以下数据已保存在剧集侧或会随工作台数据返回：剧本文本与场景、已保存的分镜偏好、目标时长、时长模式、内容语言、素材及项目风格。服务端是否把其中每一项都写入最终 LLM 提示词，以及具体排列和权重，仍需要服务端日志、代码或供应商请求记录才能确认。

特别是当前项目的 `stylePresetId = 258 / 90年代写实电影风格` 并未显式出现在 `generate-shots/async` 请求体中。服务端可以凭 `episodeId` 读取该风格，但现有证据不足以断言它把 7.2 节的整段风格原文逐字注入了“分镜剧本”提示词。风格对后续角色图、场景图、道具图及分镜图生成的影响已有直接证据；对本次文字拆镜任务的具体参与方式应保留为“服务端未公开”。

### 9.3 完整处理流程

```text
剧本、场景、素材和项目配置已保存在剧集
  ↓
用户打开“AI 拆解分镜”
  ↓
填写可选 preference，选择 standard/adaptive 与目标总时长
  ↓
POST /episodes/storyboard-preference 保存设置
  ↓
POST /episodes/generate-shots/async，仅提交 episodeId
  ↓
服务端返回 jobId，并在服务端读取剧集上下文、编译隐藏提示词、执行拆镜
  ↓
前端每 2 秒查询一次 /aivideo/episodes/job/status
  ↓
任务步骤以 STORYBOARD_BEAT 标识逐场景拆镜；允许部分场景失败
  ↓
DONE 后重新拉取工作台数据，把场景下的镜头结构展示在分镜编辑器
  ↓
用户可修改镜头描述、时长和素材绑定，也可拆分、合并、移动镜头
  ↓
单个失败场景可调用 /aivideo/scenes/rebuild-shots/async 重新拆解
  ↓
确认后调用 /aivideo/episodes/confirm-storyboard，进入视频制作阶段
```

单场景重新拆镜的真实请求为：

```json
POST /aivideo/scenes/rebuild-shots/async
{
  "id": "<sceneId>"
}
```

其任务步骤使用 `REBUILD_SCENE_SHOTS` 标识。全剧生成和单场重试都通过 `jobId` 异步执行；前端识别 `PENDING / PROCESSING / DONE / FAILED / CANCELED` 等状态，对 `STORYBOARD_BEAT` 或 `REBUILD_SCENE_SHOTS` 中失败、跳过的场景给出局部重试，而不是要求整集从头生成。

### 9.4 生成结果如何在项目中生效

生成完成后，前端不是接收一段纯文本，而是刷新剧集的场景与镜头数据，并按“场景 → 多个镜头”显示。分镜编辑器围绕以下业务信息工作：镜头序号、关联角色/场景/道具等素材、画面或视频描述、台词与音效、镜头时长，以及后续的站位图、分镜图和视频结果。

这些结构化镜头记录成为后续步骤的共同输入：

- 分镜图片生成从某一个 `shotId` 出发，并可读取或覆盖该镜头的图片提示词。
- 视频生成从镜头描述、已绑定素材、分镜图或站位图及视频参数出发。
- 修改、拆分、合并或移动镜头会直接改变后续图片和视频任务所使用的镜头上下文。
- `confirm-storyboard` 固化当前分镜阶段，工作流随后进入视频阶段。

因此，本次操作的效果是把剧集级剧本转成可编辑、可绑定素材、可继续生图和生视频的镜头级数据；它不是把一段风格提示词永久附加到每个请求上。

### 9.5 与“生成分镜图片”的区别

后续单镜头生成分镜图片使用的是另一条接口：

```text
POST /aivideo/shot-storyboard-images/generate-async
```

其浏览器请求可包含：

```json
{
  "shotId": "<shotId>",
  "appId": "<可选图片模型应用 ID>",
  "prompt": "<可选、由用户编辑的分镜图片提示词>",
  "aspectRatio": "<可选画幅>",
  "resolution": "<可选分辨率>"
}
```

这条图片接口会显式接受可选 `prompt`，而刚才的分镜剧本生成接口只接受 `episodeId`。分析提示词时必须分开取证：前者可能在浏览器中看到用户覆盖后的图片提示词，后者的最终 LLM 拆镜提示词仍由服务端隐藏编译。

```text
  + 场景与参考图序号映射
  + 镜头总时间范围
  + 按时间段排列的景别、人物动作、场景、光源、构图、运镜、音效
  + 每段台词、说话角色及声音表演要求
  + 通用负向约束
```

风格 258 不是只作为一个枚举值传给视频模型。服务端把完整风格说明放在最终提示词开头，并明确要求把风格落实到角色造型、服装材质、神态动作、背景空间和整体画面气质。后续镜头段落再用 `@图片N` 绑定实际参考素材，由此同时实现“全项目视觉风格统一”和“单镜头人物、场景一致性”。

本镜头还证明同一个场景可以占用多张参考图：酒店房间映射到 `@图片2、@图片3`，高级酒店走廊映射到 `@图片4～@图片7`。角色周启映射到 `@图片1`。最终提示词在每次提及实体时重复标注对应图片编号，而不是只在开头声明一次。

### 10.4 本次失败原因及参数规则

本次任务在提示词编译并保存快照后失败，RunningHub 展示的逐字失败原因是：

```text
Current mode does not support real-person content. To enable it, set realPersonMode to true | 当前模式不支持真人素材，如需生成真人内容，请将 realPersonMode 设为 true
```

服务器快照中的 `realPersonMode` 为 `false`。这说明当前角色参考图被模型判定为真人内容，而所选 Seedance 2.0 模式没有启用真人素材开关。失败发生在视频模型内容模式校验阶段，不是提示词编译阶段；因此这条失败记录仍然提供了完整、可信的 `finalPrompt`，但没有生成出可用于画面结果分析的视频文件。

若重新生成真人参考素材，必须在模型参数中设置：

```json
{
  "realPersonMode": true
}
```

重新提交仍会触发页面显示的付费生成动作，应在实际操作前单独确认费用。LocalMiniDrama 参考这套流程时，应在发送任务前依据模型能力与参考素材类型显示真人模式选项并做前置校验，避免在昂贵的视频任务创建后才返回失败。

### 10.5 对 LocalMiniDrama 的直接参考结论

- 项目风格应作为结构化配置保存，但视频任务创建时需要把完整风格语义实际编译进最终提示词，而不能只传风格 ID 或风格名称。
- 最终提示词应生成并持久化快照，至少保存模型映射、时长、分辨率、画幅、真人模式、参考图编号映射和逐字 `finalPrompt`，便于复现和审计。
- 镜头描述应按秒级时间段组织，把景别、动作、光源、运镜、音效与台词保持在同一个时间轴中。
- 角色、场景和道具需要在提示词中使用稳定的引用编号，并在实体每次出现时重复绑定，降低多参考图串位风险。
- 通用负向约束应放在最终提示词末尾；项目或镜头存在专用负向词时，再按明确优先级合并。
- 模型能力校验必须先于付费任务提交，尤其要检查真人内容开关、参考图数量、时长、分辨率和画幅是否受当前 `appId` 支持。

### 10.6 开启真人模式后的成功重试（2026-09-07）

在不修改镜头文本、风格或素材绑定的前提下，仅将视频参数中的 `realPersonMode` 从 `false` 改为 `true` 后重新提交同一镜头。服务端返回的新记录为：
