# RunningHub 与当前项目风格模块全链路分析

> 调研对象：RunningHub AI 漫剧工作台登录态页面，以及本仓库 `LocalMiniDrama` 的前端、后端和已有生成记录。
>
> 调研时间：2026-09-06 至 2026-09-07。
>
> 本文按 Superpowers 的系统化梳理方式组织：先固定证据，再拆分交互、UI、业务状态和提示词编译，最后给出迁移路线。文中将“页面/API 直接观察到的事实”和“根据代码或对照实验得到的推断”分开，避免把未公开的服务端实现当成确定事实。

## 1. 结论先行

### 1.1 2026-09-08 落地结果

本文后半部分原先描述的迁移方案已经在当前代码中落地，当前实现口径如下：

1. 后端 `stylePresets.v1.json` 是唯一系统风格源，收录 169 个 StyleSpec；旧前端 39 风格表和旧后端预设表已从运行时代码移除。
2. 项目以 `dramas.style_id` 保存唯一风格。新建项目必须选择有效风格；项目内图片、视频、资产和分镜请求不能以请求字段覆盖项目风格。
3. 中文说明用于用户识别；`promptZh` 和 `promptEn` 是生成约束。编译器根据模型语言能力选择中文、英文或混合模式，再将风格置于最终提示词首段。
4. 图片编译器覆盖角色单图/转面图、人物状态、场景普通/多视角/全景/俯视、道具和分镜帧；视频编译器统一组合风格、镜头动作、引用槽位、时间线、逐字对白、音频、输出和负向约束。
5. 主图片任务和视频任务会在调用供应商前保存最终提示词、负向词、StyleSpec 版本、引用清单、模型配置与能力校验快照。历史任务不会因项目之后切换风格而变化。
6. 外部 AI JSON 已升级为 v2 `prompt_contract: base_prompt`。外部结果只负责 `base_image_prompt` / `base_video_prompt`，不能携带风格覆盖或最终提示词；预览与导入均不会创建生成任务。
7. 前端风格库采用四列视觉卡片、全部/真人/3D/2D/我的分类、搜索、选中态、详情抽屉和结构化自定义风格；详情可查看中文说明及实际中英文提示词。
8. RunningHub 预览图采用本地清单治理：12 张来自已核验真实画风库截图裁图，157 张是明确标记的回退图。由于登录标签属于另一个浏览器会话，自动化无法读取其网络响应，故未把回退图标记为 RunningHub 原图。

当前完整可导出的程序风格目录见 [LocalMiniDrama风格目录v1.json](./LocalMiniDrama风格目录v1.json)，预览证据状态见 `backend-node/src/catalog/stylePreviewManifest.v1.json`。

RunningHub 的成熟点不在于“有一段更长的风格词”，而在于把风格做成了一条贯穿项目生命周期的生成协议：

1. 在项目/剧集层选择风格，风格随项目上下文继承到角色、场景、道具、分镜和镜头视频。
2. 页面只提交业务对象、素材引用和生成参数；服务端根据项目上下文编译最终提示词，客户端不负责拼接完整视频提示词。
3. 风格不是一个短标签，而是结构化的设计约束，包含画面气质、色彩、光影、镜头、环境和“必须落实到角色/服装/动作/背景”的执行规则。
4. 生成任务会保存逐字 `promptSnapshot.finalPrompt`、模型、时长、分辨率、画幅、参考图映射和模式开关，失败任务也保留快照，便于复现和排障。
5. 模型能力校验独立于提示词编译。真实对照实验中，关闭“真人模式”会失败，打开后成功；两次的最终提示词逐字一致，说明风格编译和模型能力门禁是两个阶段。

当前 LocalMiniDrama 已经具备不少正确基础：风格元数据持久化、前后端风格表、图片提示词二阶段编译、角色/场景提示词复用、H3 不可变草稿和异步任务状态。但视频普通路径仍主要是 `Style: ...` 追加，图片和视频也没有完全共享一个带版本的风格编译器。因此最值得学习的方向，是把现有能力统一为“StyleSpec → Resolver → Compiler → Snapshot → Provider”的链路。

## 3. RunningHub 的项目整体业务流程

### 3.1 页面信息架构

RunningHub 工作台的核心不是单一“生图页”，而是一个以项目和剧集为根的制作状态机。可以抽象为：

```text
项目
 ├─ 项目/剧集设置：风格、画幅、时长、语言、生成偏好
 ├─ 剧本：梗概 → 剧本/集数
 ├─ 设定：角色、场景、道具等资产
 ├─ 分镜：镜号、景别、机位、动作、对白、音效、引用素材
 └─ 短片/镜头：按分镜选择视频模型并生成、重试、查看历史、导出
```

页面顶部通过步骤导航在“剧本 / 设定 / 分镜 / 短片”等阶段间切换。每一步都围绕同一个 `projectId + episodeId` 工作，因此资产和风格不需要在每个生成弹窗中重复输入。

### 3.2 从创意到成片的状态流

1. 创建项目和剧集，设置题材、画幅、时长和整体风格。
2. 输入或生成剧本，系统提取角色、场景、道具并进入资产设定阶段。
3. 为资产生成规范参考图：角色通常是统一多视图，场景可以是普通、全景或俯视空间图，道具是独立资产图。
4. 生成分镜剧本，把每个镜头的角色、场景、道具引用、动作、台词和音效落到结构化记录。
5. 在分镜页生成镜头首帧/关键帧或分镜图，检查构图、角色一致性和场景连续性。
6. 点击“生成镜头”，选择视频模型、时长、分辨率、画幅等参数；服务端把当前项目风格、镜头文本和参考图编译成视频提示词。
7. 任务进入排队、运行、成功或失败状态；成功结果加入历史并可选择为当前镜头结果，失败可在调整参数或能力开关后重试。
8. 后续进入镜头串联、音频和成片阶段。每个阶段仍然引用前一阶段的稳定资产 ID，而不是重新依赖显示名称。

### 3.3 UI 与业务状态的对应关系

| UI 区域 | 用户动作 | 业务对象/状态 | 需要持久化的内容 |
| --- | --- | --- | --- |
| 项目/剧集设置 | 选择风格、画幅、语言、时长 | `project/episode settings` | 稳定风格 ID、完整风格文本、画幅等 |
| 资产卡片 | 生成、重生成、查看参考图 | `character/scene/prop` | 规范描述、提示词、图片历史、当前选中图 |
| 分镜卡片 | 编辑动作、台词、引用素材 | `shot/storyboard` | 结构化字段、引用关系、首帧/尾帧 |
| 生成镜头面板 | 选模型、参数、真人模式、提交 | `shot-video task` | 请求参数、最终提示词快照、状态、结果 URL |
| 历史/候选区 | 预览、选择、重试、取消 | `generation history` | 任务 ID、provider task ID、错误信息和选中结果 |

这套映射让 UI 不只是“调用按钮”，而是一个可恢复的任务控制台：刷新页面后仍能从任务记录恢复进行中、成功和失败状态。

## 4. RunningHub 风格模块的交互与 UI

### 4.1 风格选择的用户心智模型

用户在项目或剧集层选择一次“90年代写实电影风格”等预设。选择器展示风格名和视觉预览；模型、画幅、时长等是独立的生成参数。这样用户理解的是“本项目采用什么视觉设计”，而不是“每次调用 API 时手写一段 prompt”。

风格可以被看成一个继承上下文：

```text
项目风格
   ↓ 继承
角色 / 场景 / 道具 / 分镜图 / 视频镜头
   ↓ 可叠加
对象描述、镜头动作、对白、参考图、负向约束
```

### 4.2 真实风格块的结构

本次真实生成使用的风格是 `258 / 90年代写实电影风格`。服务端最终视频提示词开头实际出现：

```text
本镜头为视频镜头，整体风格：90年代写实电影风格：强调胶片颗粒、年代色偏、生活化场景、旧广告牌、钨丝灯、街头烟火气和真实抓拍感，画面应有怀旧质感、轻微褪色、柔和动态模糊和时代记忆。
核心描述：90年代写实电影风格，适合角色资产生成、风格化提示词和短片视觉统一。
色彩关键词：胶片暖黄、褪色绿色、钨丝灯橙、旧照片灰调。
光影关键词：自然窗光、钨丝灯、街灯反射、轻微过曝。
镜头关键词：胶片抓拍、生活化中景、轻颗粒、纪实构图。
环境关键词：旧街道、霓虹招牌、老式室内、年代道具。
生成时必须把这些风格特征落实到角色造型、服装材质、神态动作、背景空间和整体画面气质中，而不是只写风格名称。
```

这段内容可拆成六个业务槽位：

| 槽位 | 作用 | 90 年代电影风格中的例子 |
| --- | --- | --- |
| 名称/摘要 | 让用户和任务日志可读 | `90年代写实电影风格` |
| 核心气质 | 定义整体视觉方向 | 怀旧、真实抓拍、年代记忆 |
| 色彩 | 约束主色和色偏 | 胶片暖黄、褪色绿色、钨丝灯橙 |
| 光影 | 约束照明来源和曝光 | 自然窗光、钨丝灯、轻微过曝 |
| 镜头 | 约束摄影语言 | 胶片抓拍、生活化中景、轻颗粒 |
| 环境/执行规则 | 将风格落到对象和空间 | 旧街道、年代道具；不得只写风格名 |

### 4.3 风格不是“最后一句 Style”

真实快照表明，风格块在视频提示词的最前面，随后才是角色和场景引用、时间轴动作、对白/声音以及禁止项。它承担“全局约束”的作用，而不是把一句 `Style: cinematic` 放在正文末尾。

因此，成熟的 UI 应至少支持：

- 当前风格卡片和稳定 ID；
- 查看完整风格提示词；
- 显示当前模型是否支持该风格所需的参考图/真人/时长能力；
- 生成前查看“编译后提示词”或摘要；
- 生成后查看与任务绑定的逐字快照。

## 5. RunningHub 图片生成流程

### 5.1 资产提示词的通用编译顺序

角色、场景和道具虽然 UI 不完全相同，但可以抽象成同一条链：

```text
原始业务描述
 → 文本模型规范化（外观、材质、空间、时代等）
 → 注入项目风格块
 → 加入输出版式/视角模板
 → 加入参考图或身份一致性约束
 → 加入负向约束
 → 保存 compiled/polished prompt
 → 提交图片模型并记录结果
```

### 5.2 角色

角色资产需要解决“同一个人可被多个镜头复用”。因此风格必须进入发型、服饰材质、脸部气质、姿态和四视图统一约束，而不是只作用于背景。真实案例中的角色提示词使用统一多视图/`TURNAROUND` 结构，并把风格放在高优先级位置。

### 5.3 场景

场景除了普通单图，还需要全景和俯视空间图。不同模式的业务意义不同：

- `NORMAL`：为镜头提供常规背景和构图参考；
- `PANORAMA`：建立 360° 空间连续性，重点是环境边界和方位；
- `TOP_DOWN`：建立俯视平面关系，重点是空间布局、入口、家具和可走动区域。

三种模式应共享风格块，但使用不同的版式模板，避免将“俯视”误当作普通场景的一个形容词。

### 5.4 道具

道具提示词需要把风格落实到材质、磨损、年代、色泽和拍摄背景，同时保证道具轮廓清晰、无遮挡、可在分镜中作为参考图识别。道具通常继承项目风格，不应与角色/场景使用另一套默认风格。

### 5.5 结果与历史

图片生成不应只保存最终图片 URL。至少应保存：原始业务描述、规范化描述、最终提示词、风格 ID/版本、模型、尺寸、参考图指纹、状态和错误。这样当用户重新生成或替换参考图时，可以判断是输入变了、风格变了还是模型失败。

## 6. RunningHub 视频生成流程

### 6.1 UI 操作链

真实分镜页的操作可还原为：

1. 进入分镜镜头卡片，确认角色/场景引用和动作文本。
2. 在视频设置中选择 `seedance2.0/多模态视频`、时长、画幅/分辨率等。
3. 如参考图含真人内容，打开“真人模式”。这不是风格选择，而是模型能力/内容模式开关。
4. 点击“生成镜头”，页面提交镜头 ID、应用/模型 ID 和模型参数。
5. 服务端读取剧集风格、素材引用、镜头动作、对白和负向规则，编译 `finalPrompt`。
6. 创建异步任务，前端轮询状态并展示排队、运行、成功/失败、重试和历史。

标准入口并未把完整 `promptOverride` 或 `styleId` 直接交给页面提交；这说明风格解析和最终提示词编译发生在服务端上下文中。

### 6.2 真实请求/结果对照

本次“房客”镜头 1-1 的两次请求具有同一镜头、模型、时长、分辨率、画幅和 `finalPrompt`：

| 对照项 | 第一次 | 第二次 |
| --- | --- | --- |
| `realPersonMode` | `false` | `true` |
| 任务状态 | `FAILED` | `DONE` |
| 失败原因 | 当前模式不支持真人内容 | 无 |
| 风格 | 258 / 90 年代写实电影 | 相同 |
| `promptSnapshot.finalPrompt` | 相同 | 相同 |

因此可以确定：

- 风格编译在任务创建/模型调用前完成，并独立保存快照；
- 真人模式只改变模型能力门禁，不会重写电影感风格、镜头时间轴或参考图编号；
- 失败任务也值得保存最终提示词，因为它能直接解释“提示词是否正确、为什么模型没接收”。

### 6.3 视频最终提示词的分层结构

真实 `finalPrompt` 的业务结构是：

```text
镜头类型 + 全局风格块
 → 角色引用与场景引用（@图片N）
 → 时间轴（0-4、4-8、8-12 秒）
 → 每段景别、动作、运镜、光源和声音
 → 分段台词及语气
 → 禁止项/负向约束
```

特别值得学习的是 `@图片N`：它不是随意的文案标签，而是参考图注册表的稳定序号。提示词正文、图片列表和服务端请求必须使用同一映射，否则模型会拿错角色或场景。

## 7. 当前 LocalMiniDrama 的风格业务流程

### 7.1 风格选择和保存

前端 `frontweb/src/constants/styleOptions.js` 维护静态风格目录，每个选项含 `label`、`value`、中文 `prompt`、英文 `promptEn`、颜色和缩略图。`StylePickerButton.vue` 提供搜索、分类、预览、选中态和自定义风格输入。

项目详情页和一键生成页都通过 `StylePickerButton` 选择风格；保存时同时保留：

```text
dramas.style                 稳定短值/兼容旧数据
dramas.metadata.style_prompt_zh
dramas.metadata.style_prompt_en
```

这套“双层存储”是正确方向：短值适合筛选和兼容，完整文本适合编译和审计。

### 7.2 后端风格解析优先级

`backend-node/src/utils/dramaStyleMerge.js` 当前采用以下优先级：

1. `metadata.style_prompt_zh/en` 的完整文本；
2. 旧数据中的预设 key，匹配 `generationStylePresets.js` 后展开为中英文提示词；
3. 旧数据中的自定义文本，若没有完整 metadata，不把短的 `custom` 误当成完整风格；
4. 未知旧文本作为中英文兜底。

这解决了历史项目、预设风格和自定义风格共存时的兼容问题，也使项目风格能在不同生成入口被统一解析。

### 7.3 当前图片链路：已经接近成熟模式

#### 角色

`characterLibraryService.js` 的 `generateCharacterPromptOnly()` 先调用文本模型将外貌整理成统一四视图描述，再由 `buildFourViewImagePrompt()` 组装：

```text
【画风·最高优先级】四格统一：{stylePromptZh}
MANDATORY ART STYLE (all 4 panels): {stylePromptEn}
 → 角色布局/四视图系统规则
 → AI 规范化后的角色描述
 → Reiterate: same art style as above (...)
```

完整提示词写入 `characters.polished_prompt`。后续真正生图优先复用这段已保存提示词，避免每次生成发生漂移。

#### 场景

`sceneService.js` 对四视图和单图分别编译，均把风格置于高优先级，并补充 `No people, no text`。场景描述先经过文本模型，再套用 `NORMAL / PANORAMA / TOP_DOWN` 等版式语义，最终保存到 `polished_prompt` 或 `polished_prompt_single`。

#### 道具

道具沿用项目风格和图片生成服务，但当前需要进一步确认各入口是否全部保存了同一套风格元数据和编译版本，避免部分道具走“简单描述 + style”路径、部分道具走完整模板路径。

### 7.4 当前视频链路：两条路径并存

前端 `useVideoGenerationPanel.js` 会从 `universal_segment_text`、`video_prompt`、`polished_prompt`、`image_prompt`、`description` 等字段解析业务提示词，并构造模型、尺寸、时长、参考图、连续帧等参数。

后端 `unifiedVideoGenerationService.js` 目前有两种行为：

- 普通路径：`appendStyle(prompt, style)` 在业务提示词末尾追加 `. Style: {cleanStyle}`；
- H3 路径：读取不可变草稿中的 `final_compiled_prompt`，验证哈希、引用标签和音频语义后原样提交。

H3 路径在可追溯性上很强，但普通路径和 H3 路径的风格编译规则不完全一致。普通路径还缺少 RunningHub 那种“风格块 + 时间轴 + 参考图注册表 + 能力预检 + 快照版本”的统一协议。

### 7.5 当前项目的完整生成流水线

`useCanvasEpisodeGenerate.js` 会把项目风格、画幅、时长、旁白/全能模式等选项传给分镜生成和后续流水线：

```text
项目风格设置
 → 剧本/分镜结构化
 → 角色/场景/道具提示词和图片
 → 分镜图/首尾帧
 → 视频提示词面板
 → H3 或普通视频生成
 → 任务轮询、历史和成片
```

当前项目已经有统一任务状态、并发控制、失败重试、参考图标签和 H3 语义校验，这是学习 RunningHub 的有利基础。

## 9. 当前项目可直接吸收的成熟经验

### 9.1 把风格从字符串升级为 StyleSpec

建议在保留现有 `style` 和 metadata 的同时，规范化为：

```json
{
  "id": "cinematic",
  "label": "电影感",
  "version": 1,
  "zh": {
    "summary": "电影级大片画面",
    "palette": ["胶片颗粒", "专业调色"],
    "lighting": ["戏剧性布光", "自然窗光"],
    "camera": ["35mm 胶片", "宽画幅银幕比例"],
    "environment": [],
    "enforcement": "必须落实到角色、服装、动作、背景和整体气质"
  },
  "en": {},
  "source": "preset"
}
```

自定义风格也走同一结构，避免预设有完整模板、自定义只有一行文本。

### 9.2 统一 Resolver 和两个 Compiler

建议抽出三个稳定接口：

```text
resolveStyle(project, episode, override) -> ResolvedStyle
compileImagePrompt(context, resolvedStyle, imageMode) -> CompiledPrompt
compileVideoPrompt(context, resolvedStyle, videoMode) -> CompiledPrompt
```

两个 compiler 可以共享：风格块、参考图注册、负向约束、快照元数据；图片和视频再分别追加四视图/全景/俯视模板或时间轴/音频模板。

### 9.3 引入编译快照和版本

每次真正提交 provider 前保存：

```json
{
  "compiler": "video",
  "compilerVersion": "1.0.0",
  "style": {"id": "cinematic", "version": 1, "zh": "...", "en": "..."},
  "sourcePrompt": "...",
  "finalPrompt": "...",
  "negativePrompt": "...",
  "references": [{"index": 1, "type": "character", "id": "...", "label": "周启"}],
  "model": "...",
  "duration": 12,
  "resolution": "720p",
  "ratio": "adaptive",
  "capabilities": {"realPersonMode": true}
}
```

关键是 `finalPrompt` 必须是提交前的逐字文本；`style`、`references` 和模型能力信息用于解释它是如何产生的。

### 9.4 将能力预检从“失败后提示”前移

建立模型能力注册表，至少描述：真人内容、参考图数量、首尾帧、最大时长、分辨率、画幅、音频和 H3/Omni 支持。点击生成前执行：

```text
validate(model, compiledContext)
 → 缺少真人模式：指出开关
 → 参考图超限：指出具体图片
 → 时长/分辨率不支持：给出可选值
 → 通过后创建任务
```

这样可以减少 RunningHub 真实案例中“提示词正确但模型模式拒绝”的无效等待。

### 9.5 UI 增加“风格影响可见性”

在当前 `StylePickerButton` 和视频面板之间增加一层轻量预览：

- 当前风格名称、缩略图和摘要；
- “查看完整风格提示词”；
- “本次将影响：角色 / 场景 / 道具 / 分镜图 / 视频”；
- “查看编译后提示词”折叠区；
- 当前模型能力检查结果。

这不会把复杂 prompt 强迫用户编辑，但能回答用户最关心的两个问题：风格是否真的生效，以及最终提交了什么。

### 9.6 统一状态机和历史审计

沿用当前 `generationTaskStore`，将每个任务细化为：

```text
draft → compiling → validating → queued → running → succeeded/failed/cancelled
```

失败原因至少分类为：编译失败、引用缺失、能力不支持、provider 拒绝、轮询超时、结果保存失败。历史项保留 `finalPrompt` 和快照，而不是只显示“生成失败”。

## 10. 建议的分阶段落地顺序

### P0：协议固定

- 定义 `StyleSpec`、`ResolvedStyle`、`CompiledPrompt` 和 `ReferenceRegistry` 数据结构。
- 为现有预设生成稳定 `id + version`，不破坏 `dramas.style` 和旧 metadata。
- 增加 prompt compiler version，先只读记录，不改变模型请求。

### P1：统一图片编译

- 将角色、场景、道具的风格块、版式模板、负向规则和参考图映射统一收口。
- 保留现有 `polished_prompt` 字段，同时新增结构化快照或 JSON metadata。
- 补齐普通单图、四视图、全景、俯视的测试样例。

### P2：统一视频编译

- 将普通 `appendStyle` 替换为结构化 `compileVideoPrompt`。
- H3 继续使用不可变草稿，但草稿由同一个 compiler 生成，避免两套风格语义。
- 在视频生成面板展示编译摘要和参考图序号。

### P3：模型能力和任务审计

- 建立模型能力注册表和生成前预检。
- 普通视频任务也保存 `promptSnapshot`、参考图映射、编译版本和错误阶段。
- 统一重试时的输入快照，避免重试意外读取已变更的项目风格。

### P4：UI 反馈闭环

- 风格选择器显示完整提示词和影响范围。
- 生成面板增加“编译预览/复制/查看快照”。
- 资产卡片显示当前风格版本和生成结果来源。

### P5：回归测试与观测

- 固定“电影感”“90 年代写实电影”等风格的 golden prompt。
- 校验图片和视频都包含风格块、禁止项和正确的 `@图片N` 映射。
- 对真人模式、参考图超限、时长不支持和 provider 超时做端到端测试。
- 日志记录 compiler version、style ID、任务 ID 和失败阶段，但不记录签名 URL 或 API token。

## 11. 验收清单

完成后，用户应能在不打开开发者工具的情况下回答：

- 当前项目选的是什么风格，完整风格提示词是什么？
- 角色、场景、道具和视频是否继承了同一个风格版本？
- 本次图片/视频最终提交的逐字提示词是什么？
- `@图片1` 对应哪一张图片，是否与请求图片顺序一致？
- 当前模型是否支持真人、参考图数量、时长和分辨率？
- 任务失败是提示词编译、参数能力、provider 还是轮询保存问题？
- 重试是否使用了可追溯的原始快照，而不是悄悄读取了新风格？
