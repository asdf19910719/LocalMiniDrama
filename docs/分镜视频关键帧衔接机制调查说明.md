# 分镜视频关键帧衔接机制调查说明

## 1. 调查目的

本文调查 LocalMiniDrama 当前是否存在以下能力，并说明其实际实现状态、调用流程和限制：

1. 分镜一生成视频；
2. 从分镜一的视频中截取关键帧或尾部画面；
3. 将截图保存并引用；
4. 把截图作为分镜二视频生成的参考图或首帧；
5. 支持后续分镜连续生成。

调查范围主要包括：

- `frontweb/src/views/FilmCreate.vue`
- `frontweb/src/components/video/VideoGenerationPanel.vue`
- `frontweb/src/composables/useVideoGenerationPanel.js`
- `backend-node/src/services/tailFrameLinkService.js`
- `backend-node/src/director/continuityAnchorService.js`
- `backend-node/src/routes/director.js`
- `backend-node/src/services/unifiedVideoGenerationService.js`
- 视频、分镜、导演工作流相关路由、迁移和测试文件

## 2. 总体结论

当前项目确实存在“上一分镜视频抽帧并用于下一分镜”的能力，但不是一套统一且默认自动执行的流水线，而是并存三种实现：

| 方案 | 当前状态 | 是否从视频抽帧 | 是否绑定下一镜 | 自动化程度 |
| --- | --- | --- | --- | --- |
| 制作页“尾帧衔接” | 已启用，可操作 | 是，后端 FFmpeg | 是，写入下一镜首帧字段 | 手动触发 |
| 导演模式“连续性锚点” | 已启用 | 是，可选择任意时间点 | 通过前端上下文带入目标分镜 | 半自动 |
| 批量视频“连贯帧模式” | 代码保留，UI 隐藏 | 是，浏览器 Canvas | 理论上作为下一镜首帧 | 自动链路尚不可靠 |

因此，当前已经具备可用的手动尾帧衔接方案，也具备更灵活的导演锚点方案；但尚不存在稳定、默认开启的“分镜一生成完成后自动抽帧并立即驱动分镜二生成”的完整无人值守流程。

## 3. 方案一：制作页“尾帧衔接”

### 3.1 前端入口

制作页在当前分镜已有视频且存在下一分镜时显示“尾帧衔接”按钮：

```vue
<el-button
  size="small"
  :loading="linkingTailFrameIds.has(sb.id)"
  @click="onLinkTailFrameToNext(sb)"
>
  尾帧衔接
</el-button>
```

位置：`frontweb/src/views/FilmCreate.vue`，约第 1528 行。

点击后，前端会：

1. 查找当前分镜的下一分镜；
2. 检查当前分镜是否有可播放视频；
3. 弹窗确认是否覆盖下一分镜当前首帧；
4. 请求后端尾帧衔接接口；
5. 成功后刷新当前分镜和下一分镜的媒体数据。

请求接口：

```http
POST /api/v1/storyboards/{storyboardId}/link-tail-frame
Content-Type: application/json

{
  "drama_id": 123
}
```

相关位置：

- `frontweb/src/views/FilmCreate.vue`，约第 6877 行
- `frontweb/src/api/storyboards.js`，约第 127 行
- `backend-node/src/routes/index.js`，约第 386 行

### 3.2 后端视频选择

后端通过以下条件查询当前分镜最新的可播放视频：

```sql
SELECT id, local_path, video_url
FROM video_generations
WHERE storyboard_id = ?
  AND status IN ('completed', 'review', 'selected')
  AND deleted_at IS NULL
ORDER BY created_at DESC
LIMIT 1
```

位置：`backend-node/src/services/tailFrameLinkService.js`，约第 6 行。

需要注意：这里按 `created_at DESC` 选择最新记录，不一定是用户在界面上当前选中的视频候选。

### 3.3 下一分镜定位

后端先读取当前分镜的 `episode_id` 和 `storyboard_number`，然后在同一集内查找编号更大的第一条有效分镜：

```sql
SELECT id, storyboard_number
FROM storyboards
WHERE episode_id = ?
  AND storyboard_number > ?
  AND deleted_at IS NULL
ORDER BY storyboard_number ASC
LIMIT 1
```

该逻辑不会跨集衔接。

### 3.4 FFmpeg 抽帧

后端要求视频已经下载到本地并具有 `local_path`。仅存在远程 `video_url`、没有本地文件时，接口会拒绝执行。

抽帧命令等价于：

```bash
ffmpeg \
  -sseof -1 \
  -i input.mp4 \
  -update 1 \
  -q:v 2 \
  -frames:v 1 \
  -y output.jpg
```

输出文件命名格式：

```text
tailframe_{当前分镜ID}_to_{下一分镜ID}_{时间戳}.jpg
```

默认保存位置：

```text
data/storage/media/images/
```

FFmpeg 路径解析优先级包括环境变量、项目 `tools/ffmpeg`、应用程序目录以及系统 PATH。项目仓库中已经包含 Windows 版 `backend-node/tools/ffmpeg/ffmpeg.exe`。

### 3.5 图片记录和分镜绑定

抽帧成功后，后端在 `image_generations` 中创建一条记录：

```text
storyboard_id = 下一分镜 ID
provider       = tail-frame
model          = tail-frame-extract
status         = completed
local_path     = media/images/tailframe_*.jpg
```

随后更新下一分镜：

```sql
UPDATE storyboards
SET first_frame_image_id = ?,
    image_url = ?,
    local_path = ?,
    updated_at = ?
WHERE id = ?
```

这意味着抽出的图片会同时成为下一分镜的：

- 首帧图片记录；
- 分镜主图 URL；
- 分镜主图本地路径。

原首帧对应的 `image_generations` 记录不会删除，所以仍可作为历史图片保留；但当前代码没有单独创建“首帧替换历史”关系记录。

### 3.6 下一分镜视频生成如何消费截图

下一分镜打开视频生成面板时，前端会优先读取绑定的首帧或分镜主图：

```js
form.imageUrl = context.imageUrl
  || storyboard.image_url
  || localStaticUrl

form.firstFrameUrl = context.firstFrameUrl
  || storyboard.first_frame_image_url
  || form.imageUrl
```

普通视频生成请求会同时传递：

```json
{
  "image_url": "抽帧图片地址",
  "first_frame_url": "抽帧图片地址",
  "reference_image_urls": ["抽帧图片地址"]
}
```

统一视频生成服务会把这些字段写入 `video_generations`，再交给具体视频 Provider。

完整流程如下：

```text
分镜一视频生成完成
        ↓
用户点击“尾帧衔接”
        ↓
后端选择分镜一最新可播放本地视频
        ↓
FFmpeg 截取视频末尾附近画面
        ↓
保存 JPG 并创建 image_generations 记录
        ↓
更新分镜二 first_frame_image_id/image_url/local_path
        ↓
前端刷新分镜二媒体数据
        ↓
分镜二视频生成读取该首帧
        ↓
作为 image_url/first_frame_url/reference_image_urls 提交
```

## 4. “尾帧”并不是真正的最后一帧

虽然代码和界面称其为“尾帧”，但当前 FFmpeg 参数使用：

```text
-sseof -1
```

这表示从视频结束前约一秒开始定位，然后输出读取到的第一帧。因此更准确的定义是：

> 视频结束前约一秒区域中的一张画面。

它不是：

- 视频最后一个可解码帧；
- 编码意义上的关键帧或 I 帧；
- 根据人物姿态、清晰度或动作状态智能选择的最佳画面；
- AI 分析后选出的连续性最佳帧。

如果视频最后一秒仍有明显动作，抽出的画面可能与真正结束状态不同。

## 5. 方案二：导演模式“连续性锚点”

### 5.1 功能流程

导演视频候选面板支持以下流程：

1. 生成一个或多个视频候选；
2. 用户选用其中一个候选；
3. 播放视频并停在目标时间；
4. 选择锚点用途；
5. 创建连续性锚点；
6. 将锚点用于下一分镜视频生成。

支持的锚点用途包括：

- `state`：状态连续性；
- `composition`：构图连续性；
- `identity`：角色一致性；
- `motion`：动作连续性。

### 5.2 时间到帧号的换算

前端监听视频当前播放时间，并结合帧率计算目标帧号：

```js
frameNumber = Math.max(
  0,
  Math.round(anchorTime * selectedFps)
)
```

位置：`frontweb/src/composables/useVideoGenerationPanel.js`，约第 690 行。

### 5.3 后端精确抽帧

后端通过帧编号选择画面：

```bash
ffmpeg \
  -y \
  -i source.mp4 \
  -vf "select=eq(n\,FRAME_NUMBER)" \
  -frames:v 1 \
  output.png
```

位置：`backend-node/src/director/continuityAnchorService.js`，约第 18 行。

与“尾帧衔接”不同，这里可以提取用户明确选中的任意帧，而不局限于视频末尾。

### 5.4 派生处理

锚点服务支持以下图片操作：

- `extract_frame`：直接抽帧；
- `upscale_2x`：两倍放大；
- `line_art`：线稿处理；
- `crop`：裁剪；
- `composition_edit`：构图裁剪和缩放。

当前前端主要暴露直接抽帧、两倍放大和线稿选项。

### 5.5 数据持久化

抽出的图片会保存为 `director_artifacts` 派生产物，记录：

- 来源视频产物 ID；
- 文件路径；
- SHA-256；
- 文件大小；
- FFprobe 信息；
- 操作类型和帧号；
- 父产物关系。

同时在 `director_anchors` 中保存：

- `source_artifact_id`；
- `derived_artifact_id`；
- `frame_number`；
- `reference_role`；
- `reference_use`；
- 来源视频哈希；
- 参数 JSON。

表结构位于 `backend-node/migrations/23_director_v1.sql`。

### 5.6 下一分镜引用流程

下一次生成请求携带 `anchorId` 后，后端查询锚点及其派生图片：

```js
structured = {
  ...structured,
  referenceImagePath: anchor.artifact_path,
  referenceRole: anchor.reference_role,
}
```

然后将锚点图片作为生成参考图输入。

### 5.7 当前限制

导演锚点本身会持久化，但“该锚点分配给哪个下一分镜”的关系没有写入 `storyboards`。前端目前主要通过页面级变量保存待使用锚点：

```js
videoGenerationSourceAnchor.value = anchor
```

或画布模式中的：

```js
directorSourceAnchor = anchor
```

因此：

- 用户仍需手动切换到下一分镜；
- 锚点没有严格绑定自然顺序中的下一镜；
- 页面刷新后待使用锚点上下文可能丢失；
- 用户也可能把锚点带到非相邻分镜。

另外，如果请求中已经存在 `referenceImageUrls`，后端会优先采用显式参考图数组，再回退到 `referenceImagePath`。这可能导致制作页原有参考图遮蔽新建的连续性锚点。导演锚点在画布模式或没有其他显式参考图时更可靠。

## 6. 方案三：隐藏的批量“连贯帧模式”

### 6.1 设计目标

项目中保留了一段更接近全自动连续生成的逻辑：

```text
分镜一顺序生成完成
        ↓
浏览器加载分镜一视频
        ↓
截取 duration - 0.5 秒处画面
        ↓
Canvas 转成 JPEG Blob
        ↓
上传到后端存储
        ↓
作为分镜二 first_frame_url
        ↓
继续生成分镜二
```

### 6.2 浏览器抽帧实现

浏览器创建一个临时 `<video>` 元素：

```js
video.crossOrigin = 'anonymous'
video.currentTime = Math.max(0, video.duration - 0.5)
```

在 `seeked` 后通过 Canvas 绘制并导出：

```js
ctx.drawImage(video, 0, 0)
canvas.toBlob(callback, 'image/jpeg', 0.85)
```

位置：`frontweb/src/views/FilmCreate.vue`，约第 5637 行。

因此该方案同样不是提取真正最后一帧，而是结束前约 0.5 秒的画面。

### 6.3 当前入口被隐藏

相关 UI 被硬编码为：

```vue
<div v-if="false" class="batch-video-options">
```

所以正常用户无法打开“连贯帧模式”。变量和批量串行代码虽然存在，但当前产品界面没有入口。

### 6.4 当前传参缺陷

抽出的连续帧被写入：

```js
image_url: vFirst
first_frame_url: vFirst
```

但是 `reference_image_urls` 仍然使用当前分镜原有参考图，而不是抽出的连续帧：

```js
let refUrls = absoluteUrl ? [absoluteUrl] : undefined
```

传统 Provider 调用路径中又存在以下优先级：

```js
image_url: input.reference_urls.length
  ? undefined
  : input.image_url

first_frame_url: input.reference_urls.length
  ? undefined
  : input.first_frame_url
```

只要 `reference_image_urls` 非空，抽出的 `image_url` 和 `first_frame_url` 就可能在 Provider 调用前被清空。最终模型收到的可能仍是分镜二原始参考图，而不是分镜一视频截图。

因此该自动链路目前不能视为可靠可用。

### 6.5 其他风险

- 浏览器抽帧依赖视频 URL 支持跨域读取；
- 远程视频缺少正确 CORS 响应头时，Canvas 会被污染并导出失败；
- 抽帧失败被 `catch (_) {}` 静默忽略，批量任务会继续使用原参考图；
- 12 秒超时后同样无明确用户提示；
- 仅经典模式应用连续帧替换，全能模式不会替换；
- 批量列表只包含尚无完成视频的分镜，部分重新生成场景无法自然衔接。

## 7. “上镜尾帧”不是视频截图

制作页还有“上镜尾帧”功能。它不读取上一镜视频，而是直接复用上一分镜预先生成的高清尾帧图片：

```text
上一分镜 last_frame_image_id
        ↓
创建当前分镜 storyboard_first 图片记录
        ↓
绑定当前分镜 first_frame_image_id
```

位置：`frontweb/src/views/FilmCreate.vue`，约第 6918 行。

它的优点是：

- 不经过视频压缩；
- 图片清晰度通常更高；
- 不需要 FFmpeg；
- 不受远程视频 CORS 影响。

它的缺点是：

- 引用的是设计阶段尾帧图，不是生成视频的实际结束状态；
- 如果视频动作、人物位置或构图偏离尾帧设计图，无法反映真实视频结果。

## 8. 视频模型兼容性

下一分镜是否严格把截图当作“第一帧”，最终取决于所选 Provider 和模型能力。

项目会根据不同协议发送以下一种或多种字段：

- `image_url`
- `first_frame_url`
- `last_frame_url`
- `reference_image_urls`

不同模型可能将它们解释为：

- 严格 I2V 首帧；
- 首尾帧约束；
- 普通构图参考图；
- 多参考图素材；
- 不支持并忽略。

因此“已传入参考图”不等价于“视频一定从该图片开始”。必须结合默认视频配置、模型能力和 Provider 适配器验证。

## 9. 已发现的主要问题

### 9.1 功能层面

1. 正式“尾帧衔接”必须手动点击，没有生成完成后的自动触发器。
2. 后端抽取的是结束前约一秒的画面，不是真正最后一帧。
3. 后端按最新创建记录选择视频，不一定选择用户当前选中的候选。
4. 只支持具有本地文件路径的视频。
5. 自动批量连贯模式 UI 被隐藏。
6. 自动批量模式存在参考图优先级缺陷，抽出的连续帧可能未进入 Provider。
7. 导演锚点没有持久化绑定目标分镜。
8. 制作页已有显式参考图时，连续性锚点可能被遮蔽。
9. 当前没有 AI 自动挑选清晰、稳定、适合连续性的最佳关键帧。

### 9.2 数据一致性

“尾帧衔接”依次执行文件写入、`image_generations` 插入和 `storyboards` 更新，但数据库操作没有包裹在统一事务内。

可能出现：

- 文件已写入但数据库插入失败；
- 图片记录已插入但分镜绑定失败；
- 重复点击产生多个抽帧文件和历史图片；
- 更新成功但 `image_updated_at` 未同步，部分缓存场景可能显示旧图。

### 9.3 参数和权限校验

`drama_id` 来自请求体，当前服务没有显式校验：

- 当前分镜是否属于该剧本；
- 下一分镜是否属于该剧本；
- 请求中的剧本 ID 是否与分镜真实关系一致。

虽然下一分镜通过同一 `episode_id` 查找，但图片记录使用的是客户端传入的 `drama_id`，建议以后从数据库关系反查，不直接信任请求体。

## 10. 建议的统一目标流程

建议后续统一为后端驱动、可配置的连续性流水线：

```text
分镜 N 视频进入 selected/completed
        ↓
确认这是用户选中的正式视频
        ↓
后端 FFprobe 获取准确时长和帧率
        ↓
按策略提取候选帧
  - 真正最后可解码帧
  - 结束前 0.25/0.5/1 秒
  - 动作稳定帧
        ↓
清晰度/人脸/运动模糊评分
        ↓
选出最佳连续性关键帧
        ↓
创建统一 continuity_asset 记录
        ↓
显式绑定 target_storyboard_id
        ↓
更新下一镜首帧或连续性参考字段
        ↓
根据模型能力选择提交方式
  - first_frame_url
  - reference_image_urls
  - Provider 专用首帧字段
        ↓
可选：自动启动下一镜生成
```

建议优先处理顺序：

1. 修复批量连贯模式的参考图字段优先级；
2. 让抽帧来源使用用户选中的视频，而不是最新创建视频；
3. 将导演锚点显式绑定目标分镜并持久化；
4. 把抽帧、图片记录、分镜绑定放进可补偿事务；
5. 增加准确尾帧提取策略；
6. 按 Provider 能力映射首帧与普通参考图；
7. 最后再开放自动连续生成开关。

## 12. 最终判断

当前项目已经具备以下可用能力：

- 手动从上一分镜本地视频抽取尾部画面；
- 将截图保存为图片生成记录；
- 将截图绑定为下一分镜首帧；
- 下一分镜生成时读取并提交该参考图；
- 在导演模式中从用户指定时间点创建连续性锚点。

当前项目尚未完整具备：

- 默认开启的自动相邻分镜衔接；
