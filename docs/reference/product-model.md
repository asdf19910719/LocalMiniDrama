# RunningHub RHSTORY 产品模型

> 研究对象：RunningHub RH剧场 / RHSTORY（调研快照：2026-09-05～2026-09-09）
> 指定样例：《以我残躯护你周全》单集工作台
> 性质：基于登录态只读观察重建的产品模型，不是官方规格，也不是 LocalMiniDrama 的复制蓝图。

## 1. 结论

RHSTORY 的产品本质不是“把提示词交给模型”，而是把短剧生产组织成一个以项目和单集为边界、以确认门禁控制成本、以资产与镜头维持连续性、以异步任务和候选版本承接不确定性的生产系统。

它将创作问题拆成四个稳定阶段：

```text
剧本：讲什么、分几场
  ↓ 确认剧本基线
设定：谁、在哪里、拿什么、长什么样、什么声音
  ↓ 建立可用资产集合
分镜：每镜多长、引用什么、如何表演与运镜
  ↓ 镜头包可生成
短片：逐镜审核、连续播放、合成成片
```

这个设计有效，是因为它把高成本、非确定性的生成动作放在结构化决策之后；用户可以在真正花费算力前发现剧本、资产引用、时长或模型能力问题。

## 2. 产品解决的核心问题

### 2.1 主问题

将“文本故事”转成“可交付短片”需要跨越剧本、视觉设定、镜头设计、视频生成、审片和合成。传统生成工具通常只处理其中一个点，导致：

- 角色、场景和道具在镜头间不一致；
- 上游改稿后，下游结果是否有效不清楚；
- 每次生成缺乏明确输入、版本、价格和结果归属；
- 长流程散落在多个工具中，无法恢复进度；
- 用户不知道当前缺什么、下一步为什么被阻止。

### 2.2 RHSTORY 的解法

- 用“项目 → 单集 → 场次 → 镜头”承载叙事结构；
- 用角色、场景、道具及派生状态承载视觉真相；
- 用顶部四阶段轨道和门禁承载生产顺序；
- 用镜头检查器、分时码提示词和引用绑定组成一次生成所需的镜头包；
- 用候选、历史、确认、重拍和后处理承接模型不确定性；
- 用任务、价格与消耗明细承接云端成本和失败责任；
- 用短片时间线把单镜结果收口为整集成片。

## 3. 核心用户

| 用户 | 核心目标 | 需要的控制粒度 | RHSTORY 的响应 |
|---|---|---|---|
| 个人短剧/漫剧创作者 | 低门槛完成一集 | 流程和预设优先 | 三种创作入口、四阶段向导、批量生成、预设画风 |
| AI 导演/剪辑师 | 控制镜头、表演和连续性 | 镜头级、时码级 | 分镜三栏、资产引用、站位图、2D/3D 预演、候选历史 |
| 工作室制片 | 管多集、复用资产、核算成本 | 项目级、批次级 | 项目/剧集分层、资产库、批量任务、消耗看板、团队入口 |
| 存量内容运营者 | 将旧视频快速重制 | 批量文件级 | 视频重绘入口、按集识别、统一画风与规格 |

核心用户共同点不是“会写提示词”，而是要在有限预算和时间内得到可审核、可继续修改的影像产物。

## 4. 核心任务

1. 选择从想法、现成剧本或已有视频开始。
2. 创建项目与单集，确定画幅、语言、风格等上层约束。
3. 生成或解析剧本，按场次编辑，保存草稿并确认基线。
4. 提取角色、场景、道具，补充描述并生成/上传视觉资产。
5. 为角色配置音色，为资产选择主形象或派生状态。
6. 提取或导入分镜，调整镜头顺序与时长。
7. 为单镜绑定角色、场景、道具、图片、视频、音频和预演资产。
8. 编辑分时码提示词，选择与引用能力匹配的模型和规格。
9. 单镜或批量生成，处理失败，比较并选用候选。
10. 在短片阶段逐镜审核、连续播放，并保存为成片。
11. 在项目详情管理分镜视频、成片、图片和下载/发布出口。
12. 查看任务消耗、失败扣费状态和历史输入。

## 5. 核心实体

```text
Workspace / Space
└─ Project
   ├─ Project Style / Look Binding
   ├─ Episode[]
   │  ├─ Script Revision[]
   │  ├─ Story Scene[]
   │  │  └─ Shot[]
   │  │     ├─ Reference Binding[]
   │  │     ├─ Storyboard / Blocking / Previs
   │  │     ├─ Generation Job[]
   │  │     └─ Video Candidate[]
   │  └─ Final Cut[]
   ├─ Character[] ─ Character Appearance[] ─ Voice Profile
   ├─ Location[]  ─ Location Variant[]
   └─ Prop[]      ─ Prop Variant[]
```

### 5.1 关键语义

| 实体 | 业务职责 | 不能混同的概念 |
|---|---|---|
| Project | 聚合多集、全局画风、项目资产和经营信息 | 不是单次生成任务 |
| Episode | 独立生产进度与阶段门禁 | 不是项目的简单文本字段 |
| Script Revision | 可保存、可确认的剧本版本 | “有正文”不等于“已批准” |
| Story Scene | 叙事上的场次 | 不等于视觉“场景资产” |
| Character / Location / Prop | 稳定业务身份 | 不等于某一张生成图片 |
| Variant / Appearance | 剧情状态或视觉版本 | 不等于无语义候选图 |
| Shot | 一次镜头设计与生成边界 | 不等于单段自由提示词 |
| Reference Binding | 镜头对具体资产版本的引用 | `@图片1` 仅是显示序号 |
| Candidate | 模型生成的可比较结果 | 不应直接覆盖当前采用版本 |
| Generation Job | 一次可追踪异步执行 | 不等于最终媒体文件 |
| Final Cut | 按时间线合成的整集产物 | 不等于逐镜视频集合 |

## 6. 页面与导航架构

### 6.1 页面层级

| 层级 | 页面 | 主要责任 |
|---|---|---|
| 全站 | 开始创作、项目、资产库、工具箱、视频重绘 | 找入口、找项目、找资产、做独立试验 |
| 项目 | 项目详情 | 管多集、项目简介、图片、分镜视频和成片 |
| 单集 | 剧本、设定、分镜、短片 | 完成本集的线性生产与审核 |
| 专用工作区 | 2D 画板、3D 导演台 | 产生构图、站位、机位或运动参考 |
| 经营/治理 | 账户面板、消耗看板、水印、团队入口 | 管成本、身份、合规和空间 |

### 6.2 导航模型

- 全局导航回答“我要去哪个工作域”；
- 返回项目回答“如何离开单集但不丢项目上下文”；
- 单集选择器回答“正在制作哪一集”；
- 四阶段轨道回答“本集进行到哪里”；
- 阶段内标签和筛选回答“当前处理哪类资产/哪个场次/哪个镜头”；
- 抽屉、弹窗和历史面板回答“如何查看复杂细节而不离开当前工作对象”。

这种多层导航避免把“跨项目移动”“阶段推进”“对象选择”混成同一套菜单。

## 7. 功能模块与优先级

优先级定义：

- **CORE**：没有它就不能形成从剧本到成片的可控闭环；
- **IMPORTANT**：显著提高质量、效率、可恢复性或信任；
- **OPTIONAL**：服务特定高级场景或规模化场景；
- **VISUAL_ONLY**：只改善观感，不改变工作流能力。

| 模块 | 级别 | 判断理由 |
|---|---|---|
| 项目/单集层级 | CORE | 是所有资产、进度和产物的归属边界 |
| 剧本保存与确认分离 | CORE | 阻止未批准改动静默污染下游 |
| 角色/场景/道具资产模型 | CORE | 构成跨镜一致性基础 |
| 分镜镜头包与引用检查 | CORE | 把叙事意图变成可执行生成输入 |
| 模型能力与参数门禁 | CORE | 避免不支持引用、时长或规格的任务被提交 |
| 逐镜候选与选用 | CORE | 承接生成结果的不确定性 |
| 短片逐镜审核与成片合成 | CORE | 将单镜生成收口为用户真正需要的结果 |
| 异步任务状态与失败恢复 | CORE | 长耗时生成在刷新/失败后仍可继续 |
| 标准模式资产卡 | IMPORTANT | 为高频资产管理提供低认知负担入口 |
| 批量生成与部分失败处理 | IMPORTANT | 支持多资产、多镜头的实际生产规模 |
| 画风库与推荐模型 | IMPORTANT | 降低视觉方向选择和参数匹配成本 |
| 角色音色与试听 | IMPORTANT | 让角色身份延伸到声音一致性 |
| 消耗看板与生成前价格 | IMPORTANT（云端） | 建立对成本和失败扣费的信任 |
| 跨项目资产库 | IMPORTANT | 减少重复制作并形成可复用资产 |
| AI 项目会话 | OPTIONAL | 可辅助导航和理解，但不应成为唯一操作入口 |
| 自由节点画布 | OPTIONAL | 适合高级用户理解和编辑关系 |
| 2D 画板 / 3D 导演台 | OPTIONAL | 对复杂调度有价值，但不应阻塞普通制作 |
| 视频重绘 | OPTIONAL | 是独立内容再利用路线，不是主剧本路线必要环节 |
| 社区剧场、点赞、邀请返利 | OPTIONAL | 属于平台增长与分发，不是创作内核 |
| 暗色背景、荧光强调、圆角卡片 | VISUAL_ONLY | 可替换而不影响领域模型；其信息层级原则仍值得学习 |

## 8. 产品状态机

### 8.1 单集阶段

```text
script_draft
→ script_confirmed
→ assets_in_progress
→ assets_ready
→ storyboard_in_progress
→ storyboard_ready
→ video_in_progress
→ ready_to_export
→ exported
→ published（可选）
```

观察到的门禁是“软浏览、硬执行”：部分下游页面可提前查看，但关键输入未准备时，昂贵动作或短片阶段被禁用。这比完全锁死浏览更利于提前发现问题；但回退时必须同步 URL 并解释原因，避免地址与可见页面不一致。

### 8.2 任务状态

```text
draft → validating → quoted → queued → running
                                   ├─ succeeded
                                   ├─ failed
                                   └─ cancelled / unknown
```

批量任务还需要 `succeeded + failed + skipped` 的聚合结果，因此“部分成功”是一等状态，而不是把整个批次标成失败。

## 9. 设计为何支持工作流

1. **稳定壳层降低定位成本**：项目、单集、阶段和余额常驻，用户进入深层编辑后仍知道上下文。
2. **阶段门禁降低返工成本**：先确认剧本和资产，再做昂贵生成。
3. **列表负责扫描、抽屉负责深改**：资产卡保持可比较密度，复杂参数不挤在卡片上。
4. **单镜工作台固定选择上下文**：左栏输入、中栏意图、右栏结果、底部序列，让当前镜头的因果关系同屏可见。
5. **候选而非覆盖**：用户可以重试和比较，不会因一次模型结果失去历史。
6. **价格靠近生成动作**：把成本纳入创作决策，而不是事后账单惊喜。
7. **短片阶段由编辑转为审核**：减少无关控件，让用户关注连续播放、问题镜头和整集交付。

## 10. 证据边界

已实机/截图交叉确认：四阶段工作台、剧本草稿与重新确认、资产分类、标准/自由模式、全局画风、音色入口、分镜三栏、分时码与 `@` 引用、镜头轨、短片播放器与时间线、价格展示、消耗明细、失败不扣费样例。

尚未验证：团队权限与审批、发布审核与撤回、视频重绘内部状态机、各模型真实质量、服务端数据库结构、隐藏提示词和所有错误恢复分支。未验证项不能作为 LocalMiniDrama 的确定需求。
