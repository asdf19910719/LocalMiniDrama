# RunningHub RHSTORY 参考结论

> 目标：把参考产品的成熟经验转换为 LocalMiniDrama 的设计判断。结论不是“抄哪些页面”，而是“哪些生产问题已经被验证、哪些仍需我们自行设计”。

## 1. 一句话判断

应学习 RunningHub 的“阶段壳和生产组织”，保留并强化 LocalMiniDrama 的“本地优先、Provider 可替换、引用与生成快照、H3、Director、音频/合片/超分内核”；不应复制其云账户经营体系、即时模型/价格、社区增长机制和未验证的团队/发布能力。

## 2. 证据等级

| 等级 | 含义 | 本文使用 |
|---|---|---|
| A | 登录态实机直接可见或操作，未触发付费/删除/发布 | 四阶段、页面结构、画风库、资产/分镜/短片工作区 |
| B | 多页面、历史任务或截图互相印证 | 项目/单集层级、候选、费用、失败不扣费、产物归属 |
| C | 页面生产资源显示组件/事件存在，但未执行最终结果 | 部分裁剪、重拍、增强、批量策略 |
| D | 根据 UI 与行业生产逻辑推断 | 服务端状态机、数据表、精确失效算法 |

价格、模型、配额和画风数量都是时点快照，只能证明“能力由配置驱动、价格应前置展示”，不能成为长期常量。

## 3. 功能分类总表

| 能力 | 分类 | 对 LocalMiniDrama 的判断 |
|---|---|---|
| 项目—单集—场次—镜头层级 | CORE | 学习其清晰边界，并明确区分场次与场景资产 |
| 剧本草稿/确认 | CORE | 必须有 revision、diff、影响范围和 stale，不只复制两个按钮 |
| 四阶段 Studio Shell | CORE | 值得采用，但阶段允许软浏览、昂贵执行硬门禁 |
| 角色/场景/道具及派生状态 | CORE | 与本地现有实体统一，不新造重复数据 |
| 镜头 Inspector + 分时码 + 引用 | CORE | 结合本地 canonical reference / H3 编译内核 |
| Provider 能力驱动参数 | CORE | UI、校验、执行、快照必须共用一份能力契约 |
| 候选、选用、历史 | CORE | 保留结果谱系，禁止覆盖式重生成 |
| 短片逐镜审核与成片 | CORE | 用于收口现有视频、音频、字幕、合片和超分能力 |
| 可恢复异步任务 | CORE | 统一任务投影和刷新后对账 |
| 资产标准模式 | IMPORTANT | 高效默认入口；高级字段按需展开 |
| 批量预检与部分成功 | IMPORTANT | 范围、跳过、成本、子任务状态必须明确 |
| 画风视觉选择器 | IMPORTANT | 保留本地 StyleSpec 与编译审计，不只学缩略图 |
| 角色音色资产化 | IMPORTANT | 接入本地音频策略、试听和台词归属 |
| 跨项目资产库 | IMPORTANT | 明确引用/复制/版本与来源 |
| 消耗/成本看板 | IMPORTANT（远端生成） | 不建钱包，记录 Provider 估算/实际/未知成本 |
| AI 项目助手 | OPTIONAL | 可以辅助理解和导航，不作为唯一控制面 |
| 自由节点画布 | OPTIONAL | 做统一数据的高级投影，不与标准页双写 |
| 2D 画板 / 3D 导演台 | OPTIONAL | 输出一等预演资产，但不成为普通用户硬门禁 |
| 视频重绘 | OPTIONAL | 独立路线，先定义输入、版本和回写语义 |
| 社区、点赞、发布流 | OPTIONAL | 当前本地产品只保留导出/适配接口 |
| 暗色、荧光绿、圆角风格 | VISUAL_ONLY | 不复制品牌外观，只吸收信息层级 |
| 具体卡片封面构图 | VISUAL_ONLY | 根据本地媒体和双主题重新设计 |

## 4. 最值得学习的十项

### 4.1 用阶段组织能力，而不是把功能堆成长页

四阶段分别对应不同认知任务和完成条件。LocalMiniDrama 的现有深层能力应在阶段下被重新编排，而不是删除或重写。

### 4.2 “保存”与“批准”分开

生成工具最危险的隐性错误是把“存在内容”误判为“业务已确认”。需要 Script Revision、批准版本和下游失效范围。

### 4.3 资产是实体，图片只是版本/候选

角色、场景、道具应有稳定身份；变装、昼夜、破损等是带语义的派生状态；生成图不能直接覆盖实体。

### 4.4 分镜是 Shot Package

一次可生成镜头至少包含时长、角色/状态、场景/变体、道具、声音、分时码、构图、参考素材、模型参数和价格/能力预检。

### 4.5 失效引用必须可见

保留文字描述有助于不丢语义，但 `missing/text-fallback/stale/incompatible` 必须显示并在付费执行前处理。

### 4.6 参数表单由 Provider 能力驱动

不同模型的引用数量、输入类型、时长、分辨率、首尾帧、音频和续画能力不同。不能用一张固定表单并静默丢字段。

### 4.7 候选和历史承接模型不确定性

生成、重拍、增强都应产生新候选/新版本；“选用”才改变当前结果；重试应区分复用旧快照和使用新配置。

### 4.8 短片阶段是审核与交付，不是继续堆参数

大播放器、完成比和时间线能把注意力切换到连续性、缺失镜头和成片门禁。这是 LocalMiniDrama 现有合片能力产品化的关键。

### 4.9 批量任务要承认部分成功

批次只是聚合，子任务独立。成功结果立即可用，失败项保留输入和费用状态，并支持只重试失败项。

### 4.10 成本是生成决策的一部分

远端调用前显示 Provider、模型、数量和估算成本；执行后显示实际/未知成本和失败是否收费。本地零远端费用任务也应明确标识，而不是仿制钱包。

## 5. 不应该复制的十项

1. **不复制强制云账户和钱包**：LocalMiniDrama 的核心是本地优先，账户只应在需要远端服务时出现。
2. **不硬编码模型、价格、画幅和配额**：它们必须来自 Provider Capability 与计费配置。
3. **不把“下一步”当作批准模型**：按钮外观不能替代 revision、Gate 和依赖失效。
4. **不让引用静默降级**：文字回退必须显式接受或阻止高成本任务。
5. **不让 URL 与可见阶段不一致**：门禁回退要同步路由、状态和解释。
6. **不把标准模式和自由画布做成两套真相**：所有变更走统一领域 API。
7. **不复制无名称图标和只靠颜色的状态**：需满足键盘和可访问性。
8. **不把超长提示词当作质量保证**：重点是时间预算、引用职责和动作容量校验。
9. **不把技术增强当作内容修复万能键**：超分/去字幕不能修复角色身份、构图或剧情错误。
10. **不把未验证能力当作事实**：团队审批、发布审核、重绘内部流程和模型质量需另行专项验证。

## 6. 建议形成的本地组合模型

```text
RunningHub 式体验壳
  稳定 Studio Shell
  四阶段页面分工
  卡片扫描 + 抽屉深改
  分镜四区 + 短片时间线
  批量预检 + 成本反馈

        ×

LocalMiniDrama 式生产内核
  本地 SQLite / 文件与可恢复任务
  Provider 可替换与能力契约
  StyleSpec 与提示词编译快照
  Canonical Reference / H3 / Director
  外部 AI 包与 provenance
  TTS / 音频 / 字幕 / 合片 / 超分
```

目标不是“界面像 RunningHub”，而是让本地强能力拥有清楚的阶段、对象、状态和结果落点。

## 7. 推荐落地顺序（仅产品判断，不是实施计划）

1. 先统一 Stage、Revision、Gate、Invalidation、Capability、Job 和 Candidate 语义；
2. 再建立 Studio Shell 与剧本/设定最小闭环；
3. 再将分镜收敛为三栏 + 镜头轨，并接入引用与任务内核；
4. 再建立短片逐镜审核、时间线、Picture Lock 和 Delivery；
5. 最后补资产中心、自由画布、2D/3D、工具箱和可选生态。

这一步序避免先做漂亮页面，再发现底层没有批准、失效和候选谱系可支撑。

## 8. 开放问题

以下问题不阻塞本次产品模型，但实施前必须以本地数据和 Provider 实测回答：

- 现有旧项目如何映射 Script Revision、资产版本和 Timeline Revision；
- 各 Provider 的引用上限、时长、音频、首尾帧和取消语义；
- 200 镜项目的加载、轮询和虚拟化基线；
- 外部网页生成在登录失效、浏览器关闭和重复回填时的恢复；
- 音频、字幕、合片和超分的统一任务/候选边界；
- 低频旧功能应迁入高级工具、保留只读还是淘汰。

## 9. 研究限制

- 未执行任何付费生成、充值、删除、发布或水印保存；
- 未验证输出模型质量、多人协作、发布审核和重绘内部状态；
- 本次指定单集的“短片”处于禁用态，短片页面结构来自另一已解锁样例和本地截图交叉验证；
- 页面即时数据只代表 2026-09-05～09 的快照。
