# Production Studio V2.1 原版本能力去留与迁移总表

日期：2026-09-08
状态：P0 权威附件，开发前基线

## 1. 文档职责

本文逐项回答现有能力在 V2.1 中是否保留、归入哪个入口、现有本地数据如何一次性迁移，以及旧实现何时删除。只有同时给出目标入口、数据处理方式和验收编号的能力，才算已覆盖。

本文不定义 V1/V2 双轨、旧页面回退或旧 API 适配。项目尚未正式上线，V2.1 采用直接替换：保留有价值的创作能力，重做承载这些能力的页面、命令、状态和事实源。

判定口径：

- **主流程保留**：进入端到端成片主链，必须在标准模式可发现。
- **合并重设计**：能力保留，但旧的重复入口、状态或数据协议删除，由统一模块承载。
- **高级保留**：能力仍可用，但放入详情或高级区，不占主流程首屏。
- **全局独立**：保留为跨项目工具，产物必须显式进入媒体库或项目。
- **明确删除**：不再提供旧行为，也不建立兼容入口。

## 2. 一次性迁移与直接替换规则

### 2.1 开发阶段与正式切换点

- Phase 1～5 只在测试数据库或正式数据库副本上运行迁移器，不改变正式本地数据库，不切换正式路由。
- Phase 6 是唯一正式切换点。在同一次应用发布启动中完成任务冻结、备份、迁移、校验、数据库版本提交和 V2.1 路由启用；旧页面与旧写 API 不进入该发布构建。
- 不存在“只上线 Studio Shell”或逐页切换的正式里程碑，也不存在 V1/V2 feature flag、双写或旧页面回退。

### 2.2 迁移前任务冻结

迁移器在后端监听业务端口前运行。预检发现下列情况时不得开始：

- 仍有 `queued/running` Provider 任务；用户只能等待完成或明确取消。
- 存在 `waiting_external` 任务；用户可保留为可迁移等待任务，或明确放弃该 attempt，系统不得自动重提。
- WAL/SHM 尚未 checkpoint、数据库锁未释放或媒体写入仍在进行。

冻结完成后写入 `migration-state.json`，后端拒绝新的业务写入和 Provider 回填。远端任务不能在冻结后继续以旧协议回写；可恢复任务的 provider id、session、attempt 和幂等键必须进入迁移快照。

### 2.3 Schema version 与迁移 journal

- 数据库使用 `app_schema_version`，V2.1 目标值固定为 `2.1.0`。
- `backend-node/data/migrations/v2.1/migration-state.json` 是数据库外的崩溃恢复 journal，状态固定为 `PRECHECK → BACKED_UP → MIGRATING → VERIFYING → COMMITTED`，失败写 `FAILED`。
- journal 以临时文件写入并原子 rename，保存 migration id、源/目标版本、PID、时间、备份目录、数据库/WAL/SHM hash、预检与校验报告路径。
- 重复启动发现 `MIGRATING/VERIFYING` 时不得猜测成功，也不得重新执行；先验证正式库和备份，恢复到备份后才允许重试。
- `COMMITTED` 且数据库版本为 `2.1.0` 时迁移器幂等退出；数据库版本与 journal 不一致时进入恢复界面。

### 2.4 备份、空间与保留

- 备份固定放在 `backend-node/data/backups/v2.1/<migration-id>/`，包含 SQLite 主库、完成 checkpoint 后必要的 WAL/SHM、`manifest.json`、预检报告和文件 hash 清单。
- 可用空间必须不小于 `待备份字节 + max(512MB, 数据库字节 × 0.5) + 报告预计字节`；不足时在任何写入前阻止。
- 媒体文件不复制，但迁移前后记录规范路径、大小和 SHA-256；迁移事务不得移动或删除媒体。
- 首次 V2.1 成功备份永不自动删除。只能在“设置 → 高级数据工具 → 迁移与恢复记录”中经过影响预览和二次确认后人工清理。

### 2.5 迁移事务与验证

1. 备份 SQLite 并记录文件哈希、表计数和关键引用计数；
2. 扫描项目、剧集、资产、分镜、候选、任务、媒体和合片记录，生成迁移预检报告；
3. 在事务中创建 V2.1 revision、candidate、adoption、dependency 和 provenance 记录；
4. 校验表计数、主外键、current pointer、时段闭合、媒体路径、文件哈希和未知任务数；
5. 校验成功后提交数据库事务、写 `app_schema_version=2.1.0`，最后把 journal 原子更新为 `COMMITTED`；
6. 任一校验失败则回滚事务并从备份恢复，禁止进入半迁移运行态。

### 2.6 迁移 UI 与人工恢复

- 迁移前：显示数据库位置、备份位置、预计空间、对象计数、运行任务和“开始升级/退出”。
- 迁移中：显示当前阶段与已处理计数；禁止关闭窗口触发进程强杀，仍允许查看只读日志。
- 失败：只提供“查看报告、重试、打开备份目录、退出”；重试前必须先恢复备份。
- 成功：显示迁移摘要、未知/跳过项和“进入 V2.1”。进入前执行启动自检；自检失败自动恢复备份并回到失败界面。
- 应用无法打开 UI 时，提供 `npm run db:restore-v2.1 -- --backup <绝对备份目录>`。命令必须验证 manifest/hash、要求应用进程已停止，并在覆盖前再次备份当前故障库。

迁移成功后只运行 V2.1 页面、命令和事实源，不再双写旧字段、不保留旧页面回退、不生成旧格式导出。

特殊数据归档规则：

- 无结构场次的旧分镜归入本集 `未分场（迁移）`，每个旧分镜生成一个覆盖原计划时长的单时段。
- 旧分镜当前图片和视频迁为候选并标记 `adopted`，不得自动提升为 `approved`。
- 旧合片结果保留为历史 artifact，不得自动成为 Delivery Revision。
- 无法识别的旧任务保留审计状态，不自动重新提交付费生成。

替代竖切通过并完成迁移验收后，直接删除 `FilmList.vue`、`DramaDetail.vue`、`FilmCreate.vue`、旧 DramaCanvas 页面、旧写 API 和旧格式生成器；不设置 feature flag、旧 URL 跳转、双写或长期适配层。

现有磁盘上的历史项目 ZIP 不属于 SQLite 迁移输入，V2.1 不读取或升级旧 ZIP。升级界面必须明确这一边界；如仍需其中内容，用户应在切换前用当前程序导入到本地数据库。V2.1 项目归档只接受当前协议并对不支持版本返回 `ARCHIVE_VERSION_UNSUPPORTED`。

- 65 次引用覆盖 54 个唯一验收项；E2E 矩阵共有 78 个唯一验收项。
- 其余 24 个未被本表直接引用的 E2E 项属于新增领域能力或横切质量关口，不代表旧能力漏映射。
- 因此准确结论是“52 行矩阵能力全部映射且无无效引用”，不能表述为“78 个 E2E 项全部由旧功能矩阵引用”。

## 4. 明确删除的旧机制

- 图片生成成功后自动采用第一张；视频技术检查通过后自动采用。
- 向非空剧集合并、覆盖、追加或强制导入 JSON。
- FilmCreate、旧 Canvas、旧详情页之间的重复写逻辑和分散状态枚举。
- 独立于 Director Timeline 的旧合片事实源。
- 提示词来源变化后静默覆盖人工提示词。
- 前端伪造任务进度，以及多个页面各自实现暂停、批量与重生。
- 未做引用检查和恢复窗口的物理删除。
- H3 原生声音与后期 TTS 同时作为主声轨。
- 新生成 1.x/1.1 任务包或结果包。
- 独立数据模型、独立生成协议的旧 DramaCanvas。
- V1/V2 feature flag、旧页面回退、旧 URL 兼容跳转、运行期双写和旧 API adapter。

## 5. 删除与数据保护矩阵

| 对象 | 默认动作 | 被下游引用时 | 恢复 | 物理清理 |
|---|---|---|---|---|
| 项目 | 软删除/归档 | 显示剧集、任务、媒体、交付影响 | 支持 | 独立危险确认后清理项目存储目录 |
| 剧集 | 软删除 | 运行任务先取消或等待；交付物保留说明 | 支持 | 项目级清理任务执行 |
| 剧本/Look/资产/Shot revision | 不删除，标 superseded | 始终保留依赖图 | 不适用 | 仅随项目物理清理 |
| 候选 | 归档 | 已采用、锚点或时间线引用时禁止物理删除 | 支持取消归档 | 清理未引用文件 |
| Timeline/Picture/Post/Delivery revision | 不可变 | 不允许就地删除 | 从历史派生新版本 | 仅随项目物理清理 |
| 导入记录 | 不可变审计 | 永不单独删除 | 不适用 | 仅随项目物理清理 |
| 媒体文件 | 先归档 | 有任何 revision/artifact 引用则阻止 | 支持 | 引用计数为 0 且过保留期 |
| 任务记录 | 保留审计 | 不影响内容事实源 | 可重试产生新 attempt | 按日志保留策略压缩，不删除业务 artifact |

## 6. 实施阶段责任边界

- Phase 1：新事实源、命令 API、PromptStyleGate、Provider capability、引用预检；迁移器、journal、恢复工具只在数据库副本验证。
- Phase 2：Project Hub、项目详情、剧集创建六来源、五步安全导入、外部 AI 任务包与来源追溯。
- Phase 3：Script、Project Look、角色/状态/场景资产/道具、ChatGPT/API/ComfyUI 生图、资产 current 改选和剧集资产集合快照。
- Phase 4：StoryScene、Shot Package、Timed Segment、Prompt 编译、分镜图、目标视频 Recipe preflight、正式逐镜视频任务/候选/采用和高级画布。
- Phase 5：整集镜头审核、候选补充与局部重拍、连续性、音频、Director Timeline、Picture Lock、Post Revision、Delivery Revision 和最终成片；不建立第二套视频候选事实源。
- Phase 6：冻结任务，在正式数据库上原子完成备份/迁移/校验/路由切换，并删除旧页面、旧写 API、旧字段写入和旧格式生成器；不存在双轨退役期。
