## 1. 动态评审发现的缺陷（优先修复）

### D-01 🔴 素材卡片点击无法进入详情（交互主路径断裂）
- **现象**：项目素材页点击任何资产卡片无任何响应，详情视图不可达。（详情以**抽屉**呈现——首轮验证误查页面文本，修正后已浏览器实测：点击卡片打开「林夏」详情抽屉，五分区完整。）
- **根因**：卡片元素是 `<article class="project-asset-card" data-asset-open="...">`（HTML L626），而点击绑定写的是 `pageRoot.querySelectorAll('button[data-asset-open]')`（HTML L2511）——选择器要求 `button`，永远匹配不到。
- **修复（已实施 ✓）**：
  1. L2511 选择器改为 `pageRoot.querySelectorAll('[data-asset-open]')`；
  2. 卡片已有 `tabindex="0"`，补 Enter/Space 键支持（keydown 事件同 click）；
  3. 在 `.test.cjs` 增加断言：HTML 中存在 `querySelectorAll('[data-asset-open]')` 绑定且卡片标签为 article 时绑定仍生效（可用字符串断言 `assert.match(html, /querySelectorAll\('\[data-asset-open\]'\)/)`）。

### D-02 🔴 getCanvasModel 签名与场景键缺陷
- **现象**：`getCanvasModel('7','1','multi-selection')` 抛 `Unknown canvas scenario: 7`。
- **根因**：函数首个参数就是 `scenarioId`（传 `(projectId, episodeId, scenarioId)` 时实际拿到 `scenarioId='7'`）；且模型 scenarios 对象缺 `selection`、`multi-selection` 两个键（route 注册表有 19 个场景，模型只有 17 个）。
- **修复（已实施 ✓；签名勘误）**：HTML 调用为单参 `getCanvasModel(scenarioId)`，签名本身无误；实际缺陷是 scenarios 对象缺 `selection`/`multi-selection` 两键。已补齐，并增加回归测试。原文关于签名的判断有误，更正：
  1. ~~核对调用签名~~（已核实无误），统一签名（建议改为 `(projectId, episodeId, scenarioId)` 并在函数内取第三参）；
  2. 补齐 `selection`、`multi-selection` 两个场景定义（multi-selection：`selectedIds:['character-linxia','shot-03']`，提示"已多选：可批量重编译或查看影响"）；
  3. 增加测试：遍历 route 注册表 canvas 的全部 19 个场景逐一调用模型不抛错。

### D-03 ⚪ ~~项目素材页误触发剧集门禁提示~~（复核撤回：误报）
- **复核结论**：toast 的 textContent 在消失后仍留在 DOM；首轮爬虫读到的是**残留文本**。用 `show` class + 隔离等待复测，新增资产/从资产库添加/筛选均无 toast。非缺陷。
- **现象**：项目素材页点击「＋新增资产」等动作时，toast 弹出"请先确认剧本并完成本集素材检查"——这是**剧集**阶段 Gate 的 reason（model L475/L488），出现在**项目级**页面属于上下文错误。
- **修复**：在 bindPageActions 中定位引用 episode stage reason 的 showToast 分支，项目级页面的按钮不应绑定剧集 Gate 提示；新增资产/从资产库添加在项目页无前置门禁。

### D-04 ⚪ ~~project-import 的 success 场景直接导航不生效~~（复核撤回：场景名记忆错误）
- **复核结论**：该路由的终态场景名为 `succeeded`（非 `success`）；`#/projects/import?scenario=succeeded` 可正常渲染。非缺陷。
- **现象**：`#/projects/import?scenario=success` 直接导航后仍渲染 initial 阶段（ready 正常）。
- **修复**：核对 parsePrototypeLocation 对 project-import 的 scenario 参数处理与 renderLocation 的重渲染条件（key 需包含 scenarioId）；在 .test.cjs 增加 `parsePrototypeLocation('#/projects/import?scenario=success')` 返回 scenarioId='success' 的断言。

### D-05 ⚪ toast 状态残留（方法学备注）
toast 存活 1800ms，连续快速操作时旧 toast 会覆盖新操作的反馈。产品实现时每次操作应先清空再显示；原型可保持现状，不阻塞。

## 6. 场景素材业务流程对比与改造设计（2026-09-11，基于房客项目实测）

### 6.1 RunningHub 实测业务流程（场景素材如何被"使用"）

**设定页产出**：场景素材 = 图片池。酒店房间·夜：主图 + 俯视图 + 九宫格图；高级酒店走廊·夜/客房阳台·夜：主图 + 全景图 + 全景分镜图。场景无剧情状态层，图片按类型（俯视/全景/九宫格）平铺。

**分镜页消费**：分镜场景绑定 = 缩略图 + 下拉框；下拉展开为**场景参考图管理器**——场景主图 + 全部池内图片（俯视图 ✓/九宫格 ✓/格1～格9）**逐张勾选**，勾选集合即本镜生成的参考图输入；可移除场景。时段提示词以 @场景名 内联引用。

**道具对比**：道具 = 单图卡片平铺，无状态/视图/九宫格维度——素材类型的复杂度梯度：角色（多状态+音色）＞ 场景（多视图）＞ 道具（单图）。

### 6.2 我们 V2.1 现设计的问题

| # | 问题 | 严重度 |
|---|---|---|
| 1 | 分镜绑定场景是**整体绑定**：无法控制本镜用场景的哪张图（主图/俯视/全景），参考图输入不可控 | P1 |
| 2 | 场景图片组织为三层嵌套（剧情状态→视图参考→候选），认知与交互负担高于 RunningHub 的两层（场景→图片池） | P1 |
| 3 | 素材预览抽屉只读，不能勾选参考图；与 @图片N 槽位无联动 | P1 |
| 4 | 四宫格/九宫格拆分后的单格不可独立引用（RunningHub 格1～格9 可逐张勾选） | P2 |

### 6.3 改造设计

1. **场景素材模型简化为"场景 + 图片池"**：每张图带两个**可选标签**——剧情状态（如"白天营业"，仅作分组过滤）、图片类型（主图/俯视图/全景图/四宫格/拆分格N）。状态与视图降级为标签维度，不再作为引用层级；三层嵌套变两层。
2. **分镜页引用管理升级为"场景参考图选择器"**（对齐 RunningHub）：绑定场景后，素材预览抽屉展示该场景图片池，**逐张勾选**参与本镜；勾选顺序即 @图片N 槽位顺序，与中栏引用 chips 双向同步；支持从四宫格拆分单格入池。
3. **保留**：@图片N chips、缺失阻断、环境检测；四宫格拆分入口（生成后自动拆为格N 入池）。
4. **道具**：保持单图 + 候选，不引入状态/视图维度（对齐 RunningHub）。
5. **实施载体**：本改造作用于分镜页素材预览抽屉 + project-assets 场景模型的图片池结构（含九宫格拆分 API），作为分镜页实现的组成部分排期。

## 7. 角色素材实测与"主形象锚定"模型修正（2026-09-11 第二轮实测）

### 7.1 实测证据（设定页角色 tab → 周启详情）

- **主形象**概念实测存在：「当前形象 / 主形象」双概念 +「添加变装」按钮；
- **变装** = 状态（灰色棉质睡衣套装），带结构化着装描述（上装/下装/鞋子）；
- **角色三视图**生成（16:9/1k，跟随全局画风，¥0.1）；
- **结构化外貌字段**：脸型/发型/耳饰/身材/头身比/年龄/性格/时代基底/物种——生成提示词的参数化来源；
- 出镜角色在分镜页的引用形态：「周启 · 灰色棉质睡衣套装 ▶ 选择音色」——**人物状态（变装）+ 音色**一起被引用。

### 7.2 机制规则核验（回应"逐张勾选规则是否深入确定"）

**实测确认**：①分镜场景下拉（内部类名 shot-asset-picker）= 场景参考图选择器，展示场景主图 + 池内图片（俯视图✓/九宫格✓/格1～9）逐张勾选，「已选 N 项」，可移除场景；②提示词中的 @场景名（内部类名 shot-mention-chip）为引用芯片，**点击芯片会弹出同一个 shot-asset-picker**——引用芯片与选择器联动；③勾选集合决定该场景提供哪些参考图参与生成。

**此前方案中属于"我们的机制设计"而非 RunningHub 实测规则的部分（修正标注）**：
- 「勾选顺序即 @图片N 槽位顺序」：RunningHub 无槽位编号概念，其 @引用直接使用素材名（@酒店房间），@引用的出现顺序由提示词书写顺序决定。我们的 @图片N 编号体系是我们自己的槽位设计；勾选与编号的映射规则属设计决策，需在实现时明确定义（建议：勾选集合参与生成，@图片N 编号按提示词首次提及顺序分配）。
- 「与中栏 chips 双向同步」：为我们的交互设计（合理，保留），非 RH 实测行为。

### 7.3 设计修正：从"身份锚点/参考图管理"改为"主形象锚定"模型

用户直觉与 RunningHub 实测一致，原型的「身份锚点/基础身份图 + 参考图管理」表述晦涩、交互奇怪，应修正为**主形象锚定模型**：

| 层 | RunningHub 实测 | 我们 V2.1 修正设计 |
|---|---|---|
| 人物 | 主形象 + 变装（服饰）+ 三视图 + 结构化外貌字段 | 主形象（脸部/身体锚定代表图）+ 变装（状态，参考主形象生成）+ 三视图 + 结构化外貌 |
| 场景 | 主图 + 俯视图/全景图/九宫格（±拆分格） | 场景主图 + 视图图片池（类型标签：俯视/全景/四宫格格N；状态标签可选） |
| 道具 | 单图 | 主图 + 可选多角度候选（不加强制维度） |
| 引用 | 出镜角色=状态+音色；分镜场景=图片池勾选；提示词 @素材名 | 同左；@图片N 编号按提示词首提顺序分配 |

- 「身份锚点/基础身份图」一词废弃，改称**主形象**；"参考图管理"抽屉改造为各素材的**图片池管理**（生成/上传/拆分均入池）。
- 生成规则明确化：变装生成 = 主形象 + 着装描述 + 全局画风；状态图生成不影响主形象；删除主形象需先处理依赖其的变装（提示确认）。
- 本修正同步替代 §6.3 中"状态标签/类型标签"的表述细节，图片池结构不变。

## 8. 分镜图生成对比与设计增补（2026-09-11）

### 8.1 三方现状

- **RunningHub 实测**：每个镜头下有「故事板 | 分镜图」两个图片槽位（各带 生成+上传），分镜图生成后作为该镜头的参考画面；多张历史行为因示例镜头为空未能实测。
- **当前产品 V1**：已支持每镜多张候选图（历史图条：设为主图/放大/删除）、图片提示词编辑弹窗、序列图模式（单张/四宫格/九宫格）、生成通道选择、图片作为视频首帧/参考（隐式：当前主图自动作为视频参考输入）。
- **V2.1 现设计**：左栏分镜图候选区（生成/上传/缩略横滑/点开预览抽屉设为当前）、中栏分镜图提示词（自动拼装 + 手工覆盖）、生成后只追加候选。

### 8.2 设计增补（用户新增需求，全部采纳）

1. **时段提示词可引用分镜图（新增，最重要）**：时段提示词编辑器支持内联 @引用——输入 @ 弹出选择器（本镜分镜图/素材），被引用的**分镜图作为该时段视频生成的参考图输入**（对应 H3 的 FL2VA 图生视频模式）。分镜图从"隐式首帧"升级为"时段级显式参考"，不同时段可引用不同分镜图。
2. **分镜图多张 + 候选历史**：已在现设计（左栏候选区 + 历史抽屉）覆盖，确认保留；候选条目需显示其提示词摘要入口（点击查看/编辑完整提示词——预览抽屉已含）。

- 时段提示词 textarea 升级为**富引用编辑器**：输入 `@` 触发浮层，可引用：本镜分镜图（当前图与候选）、出场角色（状态图）、分镜场景（参考图池逐张）、场景道具；
