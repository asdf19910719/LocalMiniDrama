# RunningHub RH剧场短剧制作全流程交互调查

> 调查日期：2026-09-05
> 调查对象：RunningHub「RH剧场」项目《以我残躯护你周全》第 1 集
> 项目页面：`https://story.runninghub.cn/ai-comic/projects/2090093677004185602/episodes/2090093677008379905/script`
> 调查方法：在已登录 Chrome 会话中使用 Playwright/CUA 逐页操作；补充读取该页面实际加载的前端静态模块，用于核对被业务门禁锁住的短片阶段。未点击任何收费生成、批量生成、保存、确认、导出或删除操作。

## 1. 结论摘要

RH剧场的核心不是某一个生成模型，而是把短剧生产组织成四个显式阶段：

```text
剧本 → 设定 → 分镜 → 短片
```

四个阶段分别回答四类问题：

1. **剧本**：这一集讲什么，分成哪些场次；
2. **设定**：谁、在哪里、拿什么、采用什么全局画风；
3. **分镜**：每个镜头多长、引用哪些资产、人物如何站位、镜头内部如何按时间推进；
4. **短片**：逐镜生成和审核视频，再裁剪、重拍、排序、合片与导出。

其成熟度主要来自六点：

- 有明确的阶段入口和确认门禁，而不是把所有功能堆在一个长页面；
- 角色、场景、道具分别建模，并支持主形象/主场景/主道具及派生版本；
- 分镜不是只有一段自由文本，而是“时长 + 资产引用 + 时码动作 + 站位/机位 + Provider 参数”的镜头包；
- 标准模式与自由画布模式并存，兼顾普通用户和高级用户；
- 视频生成后仍有候选历史、截帧、局部重拍、裁剪、变速、画质和声音处理；
- 每次生成前展示模型、规格和费用，生成能力随 Provider 动态变化。

但它也不是可以原样照搬的最终答案。实际观察到的问题包括：

- 全局画风仍更接近“选中预设”，未看到风格样片对比、版本批准和场次级 Look；
- 未确认或未加载的资产引用会保留文字描述，能避免提示词丢失，但也可能悄悄降级为弱引用；
- 标准模式和自由模式是两套明显不同的操作表面，需要一个统一底层数据模型，否则容易产生状态分叉；
- 当前样例 16 个镜头预计 296 秒，个别单镜 22～30 秒，时码内容很重；必须依靠时长/动作容量校验，不能把长提示词等同于高质量；
- URL 写为 `step=video` 时，因前序门禁未满足实际仍显示剧本页，地址和可见阶段不一致，容易造成用户误解。

对 LocalMiniDrama 最重要的启示不是复制 UI，而是把现有分散能力收敛为一套**可确认、可失效、可追溯、可替换**的生产状态机。

## 2. 证据等级与边界

| 等级 | 含义 | 本文用法 |

- 片段重拍、高清修复、去字幕等云端任务的真实耗时和质量。

## 3. 项目总体结构与门禁

### 3.1 顶部阶段轨道

顶部固定显示：

```text
剧本 —— 设定 —— 分镜 —— 短片
```

实际状态如下：

| 阶段 | 当前可进入 | 当前样例状态 | 下一步门禁 |
|---|---:|---|---|
| 剧本 | 是 | 已有正文，可继续编辑 | 重新确认剧本 |
| 设定 | 是 | 已提取 2 角色、4 场景、3 道具，但图像为空 | 逐资产确认/进入下一步 |
| 分镜 | 是 | 已有 4 场次、16 镜、预计 296 秒 | 确认分镜进入短片 |
| 短片 | 否 | 顶部入口锁定 | 需先确认分镜 |

这里实际存在两种门禁：

- **浏览门禁较软**：即使设定图未生成，仍可以进入分镜查看已抽取的镜头结构；
- **执行门禁较硬**：短片入口显示锁定，直接导航到 `studio?step=video` 也不会显示视频工作台，而是回落显示剧本页。

这种设计的合理部分是：允许用户提前检查下游结构，但不允许在关键输入未确认时继续进行昂贵生成。需要改进的是：回落时应该同步改 URL，并明确告诉用户缺少哪一道批准。

### 3.2 项目和集切换

左上角始终显示项目名和集数下拉。本样例为：

- 项目：《以我残躯护你周全》；
- 当前集：第 1 集。

阶段状态显然以“集”为主要作用域，但角色等资产可跨集复用；角色详情中可见“出场集数”和“编辑出现场次”。这意味着平台把**资产真相**与**单集使用关系**分开管理。

## 4. 剧本阶段

### 4.1 页面布局

剧本页由两个主要区域构成：

- 左侧“分场大纲”；
- 右侧“剧本正文”编辑器。

本集共有 4 个场次、1162 字：

1. 场次一：林凡接下致命任务；
2. 场次二：禁术护身夺宝；
3. 场次三：真相揭露与药瓶之谜；
4. 场次四：夕阳下的告别。

点击左侧场次用于定位或切换正文上下文。正文是可编辑富文本/文本框，内容包含：

- 场次标题；
- 内景/外景、地点、时间；
- 出场人物；
- 对白；
- 括号中的动作和表演说明。

### 4.2 主要操作

底部可见两个不同语义的按钮：

- **保存草稿**：保存当前文字，但不代表下游认可；
- **重新确认剧本**：重新建立“这版剧本可以驱动设定/分镜”的批准状态。

这里“保存”和“确认”分开是成熟生产流程的重要特征。剧本修改后不应立即静默覆盖已完成资产和分镜；正确做法是保存新修订，然后计算对下游的影响。

### 4.3 对 LocalMiniDrama 的启示

LocalMiniDrama 当前能生成、选择、编辑和保存剧本，但主要用“是否有正文”判断完成。下一版本应补：

- 剧本 revision；
- 场次级结构化 ID；
- draft/confirmed/stale 状态；
- 修改后的影响预览；
- 只重提取受影响场次，而不是整集重做。

## 5. 设定阶段

### 5.1 页面总览

设定页路由为 `studio?step=art`。主要区域包括：

- 场次过滤器“全部场次”；
- 资产分类：角色 02、场景 04、道具 03；
- 模式切换：标准模式 / 自由模式；
- 工具：重新提取、批量生成、全局画风、画布编辑；
- 当前画风：3D国潮动漫；
- “进入下一步”按钮。

资产卡在无图状态下提供两个明显入口：

- AI 生成；
- 本地上传。

因此系统把“AI 是默认方法”与“用户可以替换素材”同时放在主路径，而不是把上传藏在高级设置中。

### 5.2 角色设定

本集提取到两名主角：林凡、苏婉儿。角色卡包括：

- 名称和角色等级；
- 主图；
- 音色选择和试听；
- 删除；
- 生成/上传入口。

打开“林凡｜主形象”详情后可见：

- 出场集数和出现场次；
- 当前主形象；
- 主形象与“添加变装”；
- 素材参考图；
- 角色描述：性别、年龄、身份、外貌、性格、服装；
- 图片模型；
- 布局“角色三视图”；
- 风格“跟随全局”；
- 生成费用；
- 生成后可用的“确认角色”和下载角色图。

角色不是一张随时覆盖的图片，而是：

```text
角色实体
├─ 主形象
├─ 变装/状态
├─ 身份与外貌文字
├─ 素材参考图
├─ 出场范围
└─ 音色
```

这非常适合 LocalMiniDrama 现有 `characters + character_variants + voice reference` 能力，但需要把“主形象”和“状态版本”的批准关系明确显示出来。

### 5.3 场景设定

本集提取到 4 个场景：

- 破败的宗门后山·日；
- 寒冰洞穴·日；
- 洞穴出口·黄昏；
- 宗门大殿前·黄昏。

“破败的宗门后山｜普通场景”详情包括：

- 出场集数和出现场次；
- 当前场景图；
- 主场景图-日；
- 添加衍生场景；
- 素材参考图；
- 场景描述；
- 图片模型；
- 布局/类型“普通场景”；
- 跟随全局风格；
- 确认和下载。

“主场景 + 衍生场景”适合表示：

- 昼/夜；
- 晴/雨/雪；
- 正常/破坏后；
- 不同机位或区域；
- 同一空间的剧情状态变化。

与 LibTV《青城夜巡人》的场景多视图经验结合后，LocalMiniDrama 不应只增加更多场景图片，而应给每张派生图标注 `view/state/time/weather`，让镜头编译器知道它的职责。

### 5.4 道具设定

本集提取到 3 个道具：黑色药瓶、冰心莲、长剑。道具详情与场景类似：

- 主道具图；
- 添加衍生道具；
- 素材参考图；
- 描述；
- 模型和全局风格；
- 出场范围；
- 确认和下载。

衍生道具不应仅表示“另一张好看的图”，而应承载剧情状态，例如：

- 药瓶封闭/开启/破裂；
- 长剑入鞘/出鞘/断裂/染血；
- 花朵完整/采摘/枯萎。

这也是保证跨镜连续性的基础。

### 5.5 全局画风

“全局画风”弹窗包含：

- 我的风格；
- 全部；
- 真人；
- 3D；
- 2D；
- 搜索；
- 大量带缩略图的视觉预设；
- 画面设置。

优点是发现成本低，远好于只显示风格名称或纯色块。缺点是实际交互仍表现为“点击即选用”，没有观察到：

- 同一主体多风格试片；
- A/B 比较；
- 版本号；
- 批准人和批准时间；
- 场次级 Color Key；
- 风格变更对旧资产的影响提示。

因此它在“风格浏览器”层面成熟，但还不是完整的 Look Approval。

### 5.6 标准模式与自由模式

标准模式提供结构化资产卡和批量操作，适合大多数用户。

切换到自由模式后，页面变为节点画布：

- 左侧资产列表；
- 中央资产节点；
- “描述 / 视觉提示词”编辑入口；
- 节点级模型选择；
- 单次费用；
- 连线样式、对齐吸附、小地图、缩放等画布工具。

打开黑色药瓶提示词编辑器时，当前表单只显示“描述”字段。由此可见自由模式更开放，但不同资产/状态下暴露的字段可能不一致。

正确吸收方式不是在 LocalMiniDrama 中再造一套独立数据库，而是：

```text
标准模式 ─┐
          ├─ 同一 Asset / Shot / Job API
高级画布 ─┘
```

两种模式只是不同视图，不能成为两套真相。

## 6. 分镜阶段

### 6.1 集级总览

分镜页路由为 `studio?step=storyboard`。顶部显示：

```text
4 个场次 · 16 个镜头 · 预计 296s
```

并提供：

- 重新提取分镜脚本；
- 导入分镜脚本；
- 批量生成；
- 场次过滤。

16 个镜头时长如下：

| 场次 | 镜头 | 时长 |
|---|---|---:|
| 1 | 1-1 / 1-2 / 1-3 / 1-4 | 22 / 26 / 18 / 22 秒 |
| 2 | 2-1 / 2-2 / 2-3 / 2-4 | 14 / 12 / 12 / 16 秒 |
| 3 | 3-1 / 3-2 / 3-3 | 24 / 22 / 30 秒 |
| 4 | 4-1 / 4-2 / 4-3 / 4-4 / 4-5 | 15 / 16 / 16 / 16 / 15 秒 |

总时长由镜头时长相加得到，不是先固定“整集必须 15 秒”再硬塞镜头。

### 6.2 单镜工作台

镜头 1-1 的工作台由三列和底部轨道组成。

左侧镜头检查器：

- 镜头号；
- 时长；
- 角色、场景、道具绑定；
- 故事板 / 分镜图切换；
- 视觉素材槽位；
- 站位图；
- 其他关系：图片、视频、音频上传；
- 3D导演台；
- 2D画板。

中间提示词编辑器：

- 使用 `0-5`、`5-14`、`14-22` 秒等时码描述；
- 用角色、场景、道具引用芯片插入语义引用；
- 编辑动作、表演、构图、运镜、对白和声音；
- 选择视频 Provider；
- 设置画幅、分辨率、时长及模型特有参数；
- 显示本次生成费用。

右侧为视频预览和生成后操作区。尚未生成时以下按钮禁用：

- 截屏；
- 片段重拍；
- 高清修复；
- 去字幕；
- 画质增强；
- 人声增强；
- 提取伴奏。

底部镜头轨道支持：

- 选择镜头；
- 前后插入新片段；
- 删除；
- 合并相邻镜头；
- 展开历史；
- 确认分镜进入短片。

相邻片段合并后若超过 30 秒，界面会禁用并提示当前没有可生成模型。这说明“业务编辑能力”受 Provider 能力上限约束。

### 6.3 资产引用的降级行为

当前角色、场景、道具图未生成，因此提示词中的引用芯片显示：

> 素材已解绑或暂未加载，但描述会保留这条引用。

这个机制有两个面：

- 好处：资产临时不可用时，镜头语义不会整段丢失；
- 风险：用户可能误以为仍在使用强视觉参考，实际请求只能依赖文字。

成熟实现必须给引用明确状态：

```text
bound-ready / bound-stale / missing / text-fallback / incompatible
```

付费生成前应阻止或要求用户显式接受降级，不能只用一行灰色提示。

### 6.4 视频模型和能力矩阵

实际下拉中包含 Seedance、万相、MiniMax H3、Vidu、快马、可灵等多种多模态/参考生视频模型。参数面板可见：

- 画幅：Auto、16:9、4:3、1:1、3:4、9:16、21:9；
- 分辨率：480p、720p、原生1080p、1080p、2K、4K；
- 时长；
- 真人模式；
- 尾帧续画；
- 视频续画（当前条件下禁用）。

这里值得吸收的是“字段随模型能力启用/禁用”，而不是把所有 Provider 都映射成相同表单。

建议 LocalMiniDrama 的能力矩阵至少包含：

```json
{
  "modes": ["t2v", "i2v", "fl2v", "ref2v", "v2v"],
  "maxReferences": 9,
  "referenceRoles": ["identity", "scene", "prop", "look", "continuity", "audio"],
  "durations": [5, 10, 15],
  "resolutions": ["720p", "1080p"],
  "supportsTailFrame": true,
  "supportsVideoContinuation": false,
  "supportsAudioReference": true,
  "supportsSegmentRetake": false
}
```

### 6.5 3D导演台

3D导演台是独立预演工作区，实际可见：

- 对象/工程列表；
- 自由视角与机位视角；
- 前、后、左、右、上、下视角和 90° 旋转；
- 视野角和相机距离；
- 背景/全景环境图；
- 球形环境和地面网格；
- 地面高度、透明度和名称显示；
- 添加、位移、灯光、机位、画幅；
- 截图、录制、保存工程。

它的业务价值不是“做完整 3D 动画”，而是先确定：

- 人物相对位置；
- 镜头轴线；
- 摄影机方向、焦段感和距离；
- 场景透视；
- 可供视频模型引用的构图图或运动参考。

LocalMiniDrama 已有 `layout_description`、Director 锚点和画布，但缺少把站位/机位预演明确建模为一等产物的 UI。

### 6.6 2D画板

2D画板实际可见：

- 无限网格画布；
- 工程列表；
- 选择、画笔、矩形、直线、橡皮、填充、文字和图片；
- 颜色和描边；
- 画笔稳定器；
- 撤销、重做、清空；
- 图层、快捷键、缩放、适配；
- 保存工程和截图。

这是一种轻量分镜/站位草图工具。它不应该和生成后的正式分镜图混为一谈，推荐数据角色为 `composition_previs`。

## 7. 短片阶段

### 7.1 实际门禁验证

顶部“短片”处于 `aria-disabled=true` 的锁定状态。直接导航到：

```text
studio?step=video
```

地址栏保留该 URL，但可见内容回落为剧本页。因此短片阶段有服务端/前端状态约束，不能仅靠猜测路由绕过。

### 7.2 页面资源中确认的短片子功能

虽然样例无法进入正式短片界面，但当前页面实际加载的生产模块中存在以下组件或事件：

- `StepVideo`；
- `VideoStageTopBar`；
- `VideoCenterStage`；
- `VideoShotRail`；
- `VideoTrimModal`；
- `VideoRetakeModal`；
- `VideoHistoryPanel`；
- `VideoPlayAllModal`。

从事件和国际化键可确认短片阶段至少设计了：

#### 生成与调度

- 单镜生成；
- 批量生成；
- 串行和并行两种批量策略；
- 批量数量/模型上限检查；
- 余额不足、超时、失败、取消、重试；
- 镜头级提示词、分辨率、画幅、时长和尾帧开关；
- 角色音色参考。

#### 候选和历史

- 每镜历史视频；
- 当前镜头选择；
- 播放整集；
- 单镜下载；
- 重新生成；
- 删除已导出的成片。

#### 镜头编辑

- 裁剪源片段；
- 拆分；
- 删除/恢复区段；
- 区段变速；
- 拖动镜头时长；
- 镜头重排；
- 局部片段重拍；
- 片段重拍时引用原视频、参考图和提示词。

#### 成片处理

- 整集导出；
- 截屏并保存到素材库；
- 高清修复；
- 去字幕；
- 画质增强；
- 人声增强；
- 提取伴奏。

以上是前端生产资源证据，不代表本次已实际执行并验证处理质量。

## 8. 提示词与引用机制

### 8.1 设定生图提示词

设定阶段以资产描述为业务源，模型和布局是编译参数：

```text
角色 = 身份/年龄/性别 + 外貌 + 性格 + 服装 + 布局(三视图) + 全局风格 + 参考素材
场景 = 地点/时代/时间 + 空间元素 + 光线/天气 + 类型 + 全局风格 + 参考素材
道具 = 名称/用途 + 形制/材质/颜色 + 状态 + 全局风格 + 参考素材
```

合理之处是三类资产分开，并允许节点级模型/布局/风格覆盖。仍缺少的成熟控制是：

- 身份、造型、风格、构图的字段级锁定；
- 主参考版本；
- 派生资产的父版本；
- 风格版本变化后的 stale 计算；
- 候选对比和批准原因。

### 8.2 视频提示词

本样例视频提示词的实际形态是：

```text
镜头目标/整体约束
@角色 / @场景 / @道具 / @音频 等语义引用
0-5 秒：景别、机位、构图、人物动作和镜头运动
5-14 秒：动作推进、对白、视线、空间关系
14-22 秒：结果状态、收束构图、声音或切点
负面与连续性约束
```

它的重点不是形容词数量，而是：

- 明确时间预算；
- 把引用和文本职责对齐；
- 让每个时间段有可实现的动作；
- 给下一镜留下可衔接的结束状态。

LocalMiniDrama 应继续使用结构化业务意图，再按 T2V/I2V/FL2V/Ref2V/H3 编译，不能把同一条长文本原样提交给所有模型。

### 8.3 引用角色类型

结合 RH剧场、LibTV 和 LocalMiniDrama 现有机制，完整引用角色应包括：

| 角色 | 目的 | 是否长期稳定 |
|---|---|---:|
| identity_master | 角色身份 | 是 |
| character_state | 服装、伤势、年龄状态 | 场次/镜头范围 |
| scene_master | 场景结构 | 是 |
| scene_view | 指定机位或区域 | 场次范围 |
| prop_master | 道具身份 | 是 |
| prop_state | 持有、开合、破损等状态 | 镜头范围 |
| look | 色域、曝光、材质、光线 | 全剧/场次/镜头 |
| composition_previs | 2D/3D 站位和构图 | 镜头范围 |
| continuity_frame | 上一镜真实生成状态 | 相邻镜范围 |
| motion_reference | 运镜或动作节奏 | 镜头范围 |
| voice | 人物音色 | 是/角色范围 |

## 9. 时长与镜头数量

本样例不是“视频总长 15 秒，因此决定有几个分镜”。实际关系是：

1. 剧本拆成场次；
2. 场次拆成镜头；
3. 每个镜头获得自己的时长预算；
4. 镜头内部的时码段适应该镜头预算；
5. 整集预计时长是镜头预算之和；
6. 相邻镜头只有在合并后不超过 Provider 上限时才允许合并生成。

因此正确的数据关系是：

```text
episode.target_duration（创作目标）
        ↕ 需要平衡
Σ scene.target_duration
        ↕
Σ shot.target_duration
        ↕
provider.duration_constraints（技术约束）
```

总长和镜头数量是双向调整，不应把任一方当作永远单向服从另一方。系统至少应检查：

- 每秒动作/对白密度；
- 内部 beat 数；
- Provider 最短/最长时长；
- 相邻镜头合并上限；
- 实际生成时长与目标时长偏差；
- 合片后的转场重叠。

## 10. 连续性不是“不同分镜自然相接”

RH剧场用多层机制降低跳变：

1. 角色、场景、道具主资产复用；
2. 角色变装、场景衍生、道具衍生表达状态变化；
3. 每镜显式绑定资产；
4. 站位图、2D画板、3D导演台固化空间和机位；
5. 时码提示词声明动作起点、过程和结束状态；
6. Provider 支持时使用尾帧续画或视频续画；
7. 生成后可截屏，作为后续镜头参考；
8. 不满意的局部用片段重拍，而不是重做全部；
9. 合片前可裁剪、拆分、变速和重排。

这比“每个片段是不同分镜，所以剪起来自然”成熟得多。

但单靠共享资产也不能保证精确连续。真正可靠的下一镜输入应是双层引用：

```text
长期锚点：人物身份 + 场景结构 + 道具身份 + Look
即时锚点：上一镜稳定帧 + 人物/道具状态 + 构图/动作接点
```

## 11. 与 LocalMiniDrama 的能力对照

| 维度 | RH剧场 | LocalMiniDrama 当前 | 判断 |
|---|---|---|---|
| 顶层流程 | 四阶段独立工作台 | 单一超长制作页 + 独立画布 | 本地需重构信息架构 |
| 保存/确认 | 多处显式确认 | 多以“有内容/有图”为完成 | 本地缺业务批准 |
| 资产类型 | 角色/场景/道具 + 派生版本 | 三类资产 + 角色状态，场景/道具版本较弱 | 可复用现有表，补统一版本 |
| 全局画风 | 丰富图形预设 | 预设图 + 自定义文本 | 本地功能接近，但同样缺 Look Approval |

## 12. 值得吸收与不应照搬

### 12.1 值得吸收

1. 四阶段工作台和顶部阶段轨道；
2. 草稿与批准分开；
3. 资产主版本 + 派生状态；
4. 标准模式 + 高级画布共用数据；
5. 镜头级引用检查器；
6. 时码化镜头提示词；
7. 2D/3D预演作为镜头资产；
8. Provider 能力矩阵；
9. 生成后局部修复与时间线；
10. 费用和执行上限预检。

### 12.2 不应照搬

1. 不把“点击风格预设”当作风格批准；
2. 不用倒计时替代人工确认；
3. 不让失效引用静默退化；
4. 不把所有模型都包装成一套相同参数；
5. 不把超长提示词当作成熟度；
6. 不让标准模式和自由画布各自保存一套数据；
7. 不用固定位置序号作为引用的唯一真相；
8. 不把技术性高清修复当作修复人物错误或构图错误的万能按钮。

## 13. 与本地既有调查的结合

本次 RH剧场调查与下列文档互补：

- `docs/research/style-prompt-pipeline-industry-review-2026-09-04.md`：给出风格、提示词、Look、色卡和行业流程基线；
- `docs/LibTV青城夜巡人视频制作流程调查说明.md`：证明多模态资产锚定和场景多视图比自动尾帧链更常见；
- `docs/LibTV秋人视频制作流程调查说明.md`：证明色卡、摄影圣经、轴线和动作结束状态具有生产价值；
- `docs/分镜视频关键帧衔接机制调查说明.md`：确认 LocalMiniDrama 已有手动尾帧和任意帧 Director anchor，但缺统一自动策略；
- `docs/superpowers/specs/2026-09-05-canonical-storyboard-reference-pipeline-design.md`：确认本地应继续以 canonical reference slots 为唯一引用真相；
- `docs/superpowers/specs/2026-09-05-cloud-video-upscale-postprocess-design.md`：确认超分应位于合片后、字幕和水印前，并保持可恢复状态。

综合结论是：LocalMiniDrama 不需要追赶 RH剧场的“功能数量”，而需要把自己已有的强能力组织成更成熟的用户流程，并补齐 Look、批准、失效和成片收口。

## 14. 最终判断

RH剧场可被概括为：

```text
结构化剧本
  → 可确认的资产设定
  → 带引用/时码/机位的镜头包
  → 逐镜生成与候选历史
  → 局部修片和时间线
  → 整集导出
```

它最值得 LocalMiniDrama 吸收的是生产组织方式，而不是具体模型或提示词长度。LocalMiniDrama 下一大版本应以“Production Studio V2”为目标，把现有 FilmCreate、DramaCanvas、Director、H3、视频合片和云超分收敛到同一套阶段状态、引用清单和不可变产物谱系中。配套设计见：

`docs/superpowers/specs/2026-09-05-production-studio-v2-design.md`
